## 修复：提问卡片不主动弹出 + 图钉（置顶）逻辑失效

**现象**：`question_requested` 到达后卡片只更新气泡计数，需手动点气泡才展开；点图钉除图标换色外没有任何行为变化。

**日志证据**（`~/Library/Application Support/BetterFocusIDE/logs/betterfocus.log`）：
00:15:53 收到 question_requested，直到 00:17:40 才有 `animateTo ... activeCard=question`；
期间 `pinned=false`。00:18:48/49 两次 togglePin 后无任何 animateTo；随后出现多组
`collapse → 0.1s 后 expand` 的成对记录。

**根因**：
1. `NotchService.showCard` 把「是否主动展开」绑定在 `pinned` 上，按需模式（pinByDefault=false
   或 userPinned=false）下交互式卡片只静默排队等悬停；而 hook 是阻塞等待回答的，超时即回落 IDE。
2. `mouseExited` 排除了 question/permission，且这些卡片从不会自动收起 → pinned 对它们完全无效果。
3. `userPinned` 一旦被手动设置就永久覆盖设置面板的 pinByDefault，开关失效。
4. `collapse()` 只在 pinned 时记录让位期，按需模式下悬停状态机立刻重开，卡片反复闪烁。
5. `NotchView` 展开态气泡与外层各挂一个 onTapGesture，同一次点击触发 collapse+toggle→expand。

**改动**（3 个文件）：
- `Services/NotchService.swift`：交互式卡片到达无条件主动弹出一次，pinned 只决定「展开后是否保持」；
  pinned 初值同步 `Settings.shared.pinByDefault`；mouseExited 对交互式卡片也安排延迟收起；
  togglePin 后即时展开/收起；设置面板改 pinByDefault 时清 userPinned；collapse 无条件记录让位期，
  并新增 manualCollapseNeedsMouseExit 防止鼠标未移出就自动重开；新增 `topic: "card"` 日志。
- `UI/NotchView.swift`：合并为单个带落点坐标的 onTapGesture，展开态仅顶部气泡区域可收起。
- `Services/SettingCatalog.swift`：更新 pinByDefault 的说明文案。

**验证**：`swift build -c debug` 通过（无警告），`./build.sh` 组装签名成功。
`swift test` 26 例中 4 例失败，均为 `SettingsTests` 里 `SettingCatalog.byKey("bodyFont")` 找不到定义——
HEAD 版本的 SettingCatalog 同样没有 bodyFont，属既有失败，与本次改动无关。

## 历史面板副文字前缀改正（提交 a4edbcb）

**问题**：历史行第二行一律以「答：」开头，但内容根本不是回答。用户指出「答：」
后面其实是自己的提问。

**根因**：`TurnNotice.body` 来自 `Transcript.last()`，而该函数的语义是
「尾部扫描（最近一条**用户**提问）」——`Transcript` 的文档注释里写得很清楚：
`first_prompt` = 会话开场用户轮次（标题），`last_prompt` = 最近一次用户轮次。
也就是说轮次完成通知的 title 与 body **都是用户侧输入**，从来没有助手回答。

**改法**：给 `HistoryEntry` 加 `kind: HistoryKind`（question / permission / turn），
前缀分别给「问：」「详情：」「用户：」。三类 body 语义本来就不同：
提问卡片是智能体问用户的问题，权限是命令/操作详情，轮次完成是用户这一轮的输入。

**顺带处理的三种隐藏条件**（都不该渲染副文字）：
1. 正文为空；
2. 正文与标题同源——单轮会话里 first == last，title 只是 body 的截断版
   （上去掉末尾「…」再判 `hasPrefix` 即可识别），否则每条都重复两遍提示词；
3. 正文是「点击跳转回 X」兜底文案（`TurnNotice.jumpHintPrefix`），读不到
   transcript 时产生；旧数据会把它存进 body，故读取时也要过滤。

**兼容**：旧 `history.json` 没有 `kind` 字段，`decodeIfPresent` 后按状态文案回退
（含「回复完成」→ turn，其余 → question），保证整个数组仍能解码，不会清空历史。

**测试** 78 → 89（HistoryEntryLabelTests 11 条：三种前缀语义、三种隐藏条件、
旧数据解码、kind JSON 往返）。

## OpenCode 完成通知彻底修复 + 跳转回终端

**症状**：桌面端与 CLI 都不弹「回复完成」；修好弹窗后又发现点通知跳到
OpenCode 桌面端，而不是用户等待的 iTerm。

**根因一：事件名随 2.2.5 变了**。旧代码监听 `session.idle` / `session.status`，
2.2.5 里**两者都不存在**了。实测（临时往插件写 `/tmp` 日志抓 RAW 事件）得到真实
事件集：`session.created / renamed / inbox.enqueued / inbox.delivered /
execution.started / step.started / text.delta / execution.succeeded`。一轮结束
的唯一信号是 **`session.execution.succeeded`**，data 只有 `{sessionID}`。
修法：`TURN_EVENTS` 集合同时容纳新旧三种，旧版作为回退。

**根因二：插件跑在桌面端常驻服务里，天然不知道终端**。`plugin list` 能看到插件，
但 setup 日志显示四个实例**全是同一个 pid**（`opencode-cli serve --service`），
它们是按 location 各加载一次；CLI 客户端自己不加载插件。事件流里也没有客户端
类型字段（`session.created` 只有 projectID / directory / model）。所以插件无法
上报 host，应用侧 `HostInfo` 为空 → 回退 `ideBundles["opencode"]` =
`ai.opencode.desktop` → 永远跳桌面端。

**根因二的解法：从进程表反推**（`OpenCodeHostProbe`）。终端里跑的 opencode
（TUI 或 `opencode run`）祖先链一定有终端 App；桌面端服务的祖先是 launchd。
- `isClient` 必须排除三类同名进程：GUI 打包进程（`.app/contents/`）、
  后台服务（`--service` / ` serve`）、本应用。否则 `OpenCode.app` 会被当成客户端。
- **必须再用 cwd 比对**：终端里的 opencode TUI 常常一整天挂着，只按祖先链判断会
  让桌面端会话也被劫持到终端。用 `lsof -a -p PID -d cwd -Fn` 取进程 cwd，
  与事件 `location.directory` 做双向包含（用户在子目录启动时 cwd 是子目录、
  上报的是项目根）。读不到 cwd 时才降级为兜底候选。

**实测验证**（fixture 进程链 + 模拟 socket 事件）：iTerm 里起
`perl -e 'sleep 240' opencode-fixture` → 链为 fixture → zsh → login → Terminal；
目录命中 `Desktop/aaaa` 时 → `source=iTerm`，不命中 → `source=OpenCode`（回退桌面端）。
注意：`ps` 的 command 列不含被 shell 吃掉的注释，用 `sh -c 'sleep 240' name` 也会被
exec 替换，最终用 `perl -e 'sleep 240' <标记>` 才让标记出现在 argv 里。

**顺带的改进**：插件现在缓存 `session.renamed` 的标题与 `session.inbox.enqueued`
的用户输入，随 `turn_finished` 的 payload 上报（`title` / `prompt` / `directory`），
`TurnNotice.parse` 在 transcript 缺失时回退用它们——否则横幅只有
「OpenCode 回复完成 / 点击跳转回 OpenCode」这类空话。

**测试** 89 → 105（OpenCodeHostProbeTests 16 条：ps 解析、三种终端命中、
服务/GUI 排除、目录命中与不匹配、cwd 缺失降级、路径双向包含）。

**操作提醒**：插件内容变更后必须 `opencode-cli service restart`，桌面端不会重启
那个长驻服务。


## 排查：opencode 报 ERR_PROXY_TUNNEL 503（环境问题，非本项目代码）

**现象**：`opencode run --model beacon/...` 报 `ERR_PROXY_TUNNEL: Proxy refused to open a tunnel:
503 Service Unavailable`。

**根因链**：
1. `beacon` 提供方的 baseURL 是内网 `https://beaconapi.bmwbrill.cn/personal/v1`；
   `curl -x 公司代理` 对该域名 CONNECT 直接回 **503**，而 `--noproxy '*'` 直连返回 401（服务健康）。
   即代理不允许隧道到内网域名，必须绕过。
2. `HTTPS_PROXY` 指向 `proxy.bmwbrill.cn:8080`，靠 `NO_PROXY` 排除内网域名才会直连。
3. **关键坑**：`opencode run` 并不自己起服务，而是复用常驻的 `opencode serve --service`
   （固定端口 49374，`~/.config/opencode/service.json`）。该服务由 OpenCode 桌面版拉起，
   `NO_PROXY` 只有 `localhost,127.0.0.1,::1` → 我在 shell 里改 `NO_PROXY` / 换 `XDG_DATA_HOME`
   全部无效，因为请求实际由那个老进程发出（日志里能看到 `Managed service port 49374 ... already in use`）。

**修复**：
- `launchctl setenv NO_PROXY` + `no_proxy` = `localhost,127.0.0.1,::1,bmwbrill.cn,.bmwbrill.cn,beaconapi.bmwbrill.cn`
  → 杀掉旧 service 重启桌面版后，新 service 继承到该值，`opencode run` 立即返回正常。
- 固化：新增 `~/Library/LaunchAgents/com.bmwbrill.proxy-env.plist`（RunAtLoad 执行 `launchctl setenv`），
  `launchctl bootstrap gui/$(id -u)` 已加载；`~/.zshrc` 的 `no_proxy` 补上裸域与显式主机名（两种写法都匹配得上）。
- 未受影响：外网域名（models.dev / registry.npmjs.org）仍走代理，正常。

**排查方法论**：先用 `curl -x` 与 `--noproxy '*'` 对比定位「代理拒绝 vs 目标故障」；
再用 `ps eww -p <pid>` 看真实发包进程的 env，别看当前 shell 的 env——桌面版/IDE 插件各自有独立进程。
JetBrains ACP 那套 `opencode serve --stdio` 同理，需重启 IDE 才继承新 env。

### 复发（同日 14:55）：根因升级为「共用后台服务的环境由启动方决定」

**再次现象**：`ERR_PROXY_TUNNEL 503` 复现，而 launchd 级 `NO_PROXY` 一直是对的。

**真正的机制**：所有 opencode 客户端共用 `127.0.0.1:49374` 上的那个 `serve --service`，
**谁先拉起谁的环境说了算**。桌面版（Electron）拉起服务时把 env 写成

实测三次桌面版拉起的服务（13890 / 85872 / 90302）全是回环-only；终端拉起的（22460 / 92902 / 95281）
全都有 `.bmwbrill.cn`。所以「终端能用、桌面版不能用」是本机稳定现象，不是偶发。

**试过但无效**：
- `launchctl setenv NO_PROXY`：改不动桌面版拉起的服务（它自己重写 env）。
- 自建 LaunchAgent 抢 49374：抢不过，桌面版/TUI 会立刻重新 spawn，

- `XDG_DATA_HOME` 隔离：仍复用 49374 上那个服务，测试无效（日志里能看到端口占用）。

**当前可用解**：`~/.local/bin/ocfix`（新增）——杀掉残留 `serve --service`，用**桌面版同版本 CLI**

**待办/可选**：若想彻底摆脱「谁先拉起」的竞态，可改为把内网请求从代理链路里摘出去——
本机跑一个本地分流代理（`*.bmwbrill.cn` 直连、其余转发上游代理），再把系统代理指向它，
这样桌面版注入的 env 也会走本地分流。本次未实施（需改系统网络设置，破坏面较大）。

## 15:40 彻底解决 opencode `ERR_PROXY_TUNNEL ... 503`（beacon 内网域名）

**为什么以前不用配**：macOS 系统代理是 **PAC**（`http://proxy.bba/proxy-mac.pac`），
第 60 行把 `*.bmwbrill.cn` 全部 `return "DIRECT"`。浏览器等走系统代理的应用天然正确。
但 **opencode 基于 Bun，不读 PAC，只读环境变量**。`~/.zshrc` 里原本是
「export 代理 + `NO_PROXY` 被注释掉」，于是内网域名也被送去公司代理，
代理拒绝为内网建隧道 → 503。

**关键澄清**：桌面版 `app.asar` 的 `zh()` 是**合并**不是覆盖——
`[...new Set([process.env.NO_PROXY, process.env.no_proxy, "127.0.0.1,localhost,::1"])]`。
asar 里 `proxy.bmwbrill` 出现 0 次，说明它从不硬编码代理地址，全部继承自启动它的进程。
所以「谁先拉起 49374 服务」决定成败，而修复点就在启动环境。

**三层配置（全部落地）**：
1. `~/.zshrc`：代理大小写变量 + 完整 `NO_PROXY`（含 `bmwbrill.cn`、
   `bmw-brilliance.cn`、`bba-app.biz/.com`、内网三段 CIDR）。
2. `~/Library/LaunchAgents/com.bmwbrill.proxy-env.plist`（RunAtLoad）：
   `launchctl setenv` 注入同一套变量，保证 **Dock 启动的 GUI 应用**也继承正确环境。

## 15:22 「Qoder IDEA 插件有些通知不是任务完成发出的」

**根因一：Stop 事件被注册了两份 betterfocus hook。**
`~/.qoder/settings.json` 的 Stop / SessionEnd / PreToolUse / PermissionRequest
各有两个 betterfocus 分组：一个指向 `~/.qoder-cn/hooks/...`（无 marker），
一个指向 `~/.qoder/hooks/...`（带 `_betterfocus_marker`）。Qoder 每个事件

**结果**：四个事件各剩 1 份，路径指向 `.qoder`；启动日志

## 15:38 `opencode serve` + 浏览器：点通知跳去了桌面端

**现象**：`opencode serve` 起服务、浏览器里用 opencode，任务完成的通知点开
跳到 OpenCode 桌面端。

**根因**：插件跑在 serve 进程里，事件流不带客户端类型；宿主探测
`isClient` 把所有 ` serve` 进程当服务端排除，于是 host 恒空 → 回退桌面端。

**改法**：
1. 插件上报 `process.pid`（`payload.pid`）。终端 TUI / 桌面常驻服务 /
   浏览器 serve 三种客户端的事件完全一样，只有进程能区分。
2. `OpenCodeHostProbe.role(of:byPid:)` 沿祖先链判定：
   `opencode serve` → `.webServe`（serve 派生的 cli 子进程也能回溯）；
   `--service` → `.desktopService`；其余 opencode 客户端 → `.otherClient`。
3. `webHost` 命中 serve 后读监听端口，`host.url = http://127.0.0.1:<port>/`。
   **lsof 必须加 `-P`**：不加时 4096 被写成服务名 `bre`，`Int()` 直接失败。
4. `IDELauncher.activate` 开头判 `host.url` → `NSWorkspace.open`，不再激活桌面端。
5. `HostInfo` 新增 `url` 并自定义解码（decodeIfPresent），历史里的旧 host 缺键也能读。
6. 判定统一收进 `OpenCodeHostProbe.resolveHost`，宿主 `name` 留空——
   徽章与来源名仍是 `OpenCode`，不会变成「浏览器」。

**验证**：模拟事件（pid=9358，即当时的 `opencode serve`）写入 history：
`host={"bundle":"betterfocus.web","url":"http://127.0.0.1:4096/","name":""}`，
source 仍为 OpenCode。测试 125 条全过（+11）。

**注意**：serve 进程里持有的是旧插件，必须重启 `opencode serve` 才会报 pid；

## 15:51 浏览器会话跳转：要切回已开的 tab，不是新开一个

`NSWorkspace.open(url)` 只会新开 tab，用户正在对话的那个页面留在后面。

**做法**：`BrowserTabFocus` 用 AppleScript 遍历候选浏览器的窗口/标签页，
按 `host:port` 命中就 `active tab index`（Chromium 系）或 `current tab`（Safari）

**要点**：
- `localhost:4096` 与 `127.0.0.1:4096` 必须都算命中（用户手敲 vs 插件上报）。
- `Target` 解析不出端口就放弃（只用主机名会误匹配整站）。
- 结果分 found / notFound / failed：notFound 才换下一个浏览器；failed
  通常是没给「自动化」权限，继续试没意义。
- 默认浏览器优先（`NSWorkspace.urlForApplication(toOpen:)` 查），其余按序。
- 脚本用 `osacompile` 验过语法（两套属性名不同，写错只静默失效）：
  Chromium `active tab index` + `minimized`；Safari `current tab` + `miniaturized`。
- Firefox / Arc 没有标签页 AppleScript 接口，会落到新开 tab（与旧行为一致）。
- 串行队列执行，连点不并发。

**待验证**：首次点击会弹「BetterFocusIDE 想要控制 Google Chrome」，
允许后才会切 tab；拒绝则静默回退到新开 tab。

**第一层**：候选浏览器只按系统默认排序，默认是 Safari 就先命中它——而 Safari

## 修复：Qoder TodoWrite 的 merge 增量语义导致进度塌缩

**根因（探针实测）**：Qoder 的 `TodoWrite` 是 Claude Code V2 血统，带 `merge` 参数：
- `merge=False`（建列表）发整表 10 条；

岛侧 `apply(snapshot:)` 是整表覆盖，把 1 条当整表 → 列表塌成 1/1，其余 9 条消失。

**关键事实**：Qoder 状态值是**大写枚举**（`PENDING`/`COMPLETE`/`IN_PROGRESS`），

## 各 IDE 的 todowrite 适配 —— WorkBuddy Task* 家族（23:00 收官）

**背景**：WorkBuddy 用 V2 `TaskCreate`/`TaskUpdate`（单条 UPSERT），与 Qoder/Claude 的 `TodoWrite` 整表覆盖不同。

**关键实测结论（探针 /tmp/bf-probe 门控，转录 .jsonl）**：
- `TaskCreate` 入参 `{subject, description, activeForm}`（无 id）；返回 `output.text = "Task #N created successfully: <正文>"`——**无结构化 task.id**。
- `TaskUpdate` 入参 `{taskId, status}`（无正文）；taskId 是 `61,62,...,70` 这类**全局递增编号**，与返回文本的 `Task #N` 显示编号**不对应**。
- 手动停止 session 时**不触发任何 hook 事件**（无 Stop/SessionEnd/PostToolUseFailure），只能靠超时兜底。

**三个坑及修法**（都在 `HostHookTemplate.swift` 的 `emit_todo_upsert`）：
1. TaskUpdate 无正文被 `if not content: return` 丢弃 → 改为「taskId→正文」磁盘持久化映射（`_TODO_STATE_DIR`）。
2. 无法从 TaskCreate 响应拿到 taskId → 用 **FIFO 队列**：TaskCreate 把 subject 压队，TaskUpdate 首次见某 taskId 时弹队认领（Agent 按列表顺序推进，顺序一致）。兼容 Qoder 有 `tool_response.task={id,subject}` 的结构化宿主。
3. 兜底 `todoIdleTimeout` 初始设 8s 太短，误伤 Agent 正常执行间隔（10~60s），导致「清空→下次 TaskUpdate 重新 append」使总数塌缩成已完成数 → 默认提到 **60s**，并补 `.turnFinished`（Stop）分支立即清 todo，兜底只管手动中断。

**显示上限**：分段条 `TodoCardLayout.maxSegments` 原为 8，10 项任务被压成 8 段、段数与总数对不上 → 提到 **16**（≤16 一段一任务，>16 才分桶）。

**通用结论**：hook 脚本是每次独立进程无内存状态，跨事件共享数据（product/taskId→正文映射）必须写盘（`~/Library/Application Support/BetterFocusIDE/`）。
