# CLI 类宿主适配经验（Claude Code / Codex / Kimi / Qoder CLI / Qoder CN CLI）

日期：2026-11-05
范围：如何在 BetterFocusIDE 里接入「没有自己窗口、跑在终端里」的编码智能体，并让卡片正确显示
**产品名 + 终端名**、显示**终端图标**、点击**回到那个终端窗口**。

---

## 1. 为什么 CLI 要单独一套规则

GUI 宿主（Cursor / Trae / WorkBuddy / Qoder IDE）报送的 `host` 就是它自己的 `.app`，
所以「名称 = host.name、图标 = host.name、跳转 = host.bundle」这条链天然成立。

CLI 宿主不成立：

| 维度 | GUI 宿主 | CLI 宿主 |
|---|---|---|
| host 是什么 | 产品自己的 `.app` | **跑着它的那个终端**（Warp / iTerm / Terminal / Ghostty / VS Code 内置终端） |
| 产品身份从哪来 | host | hook 自己（编译期写进脚本的 `PROVIDER`） |
| 卡片该显示什么 | `Trae CN` | `Qoder CLI（Warp）` |
| 图标该用哪个 | 产品图标 | **终端图标**（产品图标在终端场景里没有识别度，用户靠终端区分会话） |
| 点击该跳哪 | 产品窗口 | **终端应用窗口**（`IDELauncher` 激活 host.bundle） |

结论：CLI 的「身份」有两层——产品（谁在跑）与终端（在哪跑）。两者都要显示，缺一个用户就得猜。

---

## 2. 终端身份是怎么拿到的

hook 进程的祖先进程链：`python3 → betterfocus-notify.sh → qodercli → zsh → Warp.app/Contents/MacOS/Warp`。

`HostHookTemplate.host_app()` 逐级 `ps -o ppid/comm` 往上走，跳过 shell / 解释器
（`SKIP_COMM`），取**最外层** `.app`，读它的 `Info.plist` 得到 bundle/name。因此：

- 在 Warp 里跑 → `dev.warp.Warp-Stable` / `Warp`
- 在 iTerm 里跑 → `com.googlecode.iterm2` / `iTerm2`
- 在 IDE 内置终端里跑 → 那个 IDE 的 bundle（此时卡片标「Claude Code（VS Code）」，跳转回 IDE）

坑：**祖先链可能根本没到终端**。被别的 agent / IDE 以子进程方式拉起时，最外层 `.app`
是「启动它的那个宿主」，不是终端。所以 `AgentProvider.label` 对 CLI 产品的规则是：

```swift
if provider.isCLI {
    if let terminal = TerminalHost.displayName(...) { return "\(displayName)（\(terminal)）" }
    return provider.displayName          // 认不出终端就只写产品名
}
```

**不能退回 `host.name`**——会把「Qoder CN CLI」压成「WorkBuddy」，掩盖真正的产品。

## 3. 图标与跳转

- **图标**：`IDEIconProvider` 按 `host.name` 命中 `warp.png` / `iterm.png`；
  没有对应 PNG 的终端（Terminal.app / Ghostty / Kitty）落到灰色文字徽章。
  新增终端时**只需加图片 + 映射**，不用改命名逻辑。
- **跳转**：`IDELauncher.target(for:host:)` 在识别出终端宿主时返回 `[host.bundle]`，
  于是点通知 = 激活终端窗口。此前这里是「CLI → 无处可跳 → 返回 nil」，
  用户点击没反应；现在统一由 `TerminalHost` 判定，命名 / 图标 / 跳转共用一份名单，
  避免出现「卡片写着（Warp）但点不开」。
- 终端名单只有一处：`Models/TerminalHost.swift`。

## 4. 各宿主的真实接入方式（实测）

| 宿主 | 配置文件 | 协议 | 能拿到 | 拿不到 |
|---|---|---|---|---|
| Claude Code | `~/.claude/settings.json` | JSON，PascalCase + `hookSpecificOutput.permissionDecision` | 提问、权限提醒、回合完成、会话结束 | — |
| WorkBuddy | `~/.workbuddy/settings.json` | 同上 | 同上 | — |
| Cursor | `~/.cursor/hooks.json` | JSON，camelCase，权限类必须回 allow/deny | 回合完成、会话结束 | 提问、权限（回了就等于替用户审批） |
| Trae / Trae CN | `~/.trae{,-cn}/hooks.json` | JSON + `version:1`，PascalCase | 提问、权限提醒、回合完成 | **没有 SessionEnd**（只有 6 类事件） |
| Kimi Code CLI | `~/.kimi-code/config.toml` | TOML `[[hooks]]` 数组表 | 提问、权限提醒、回合完成、会话结束 | — |
| Codex CLI | `~/.codex/config.toml` 的 `notify` | 外部程序，payload 走 **argv** | 回合完成 | 提问、权限（TUI 内自审，无事件） |
| Qoder / Qoder CN | `~/.qoder{,-cn}/settings.json` | JSON + matcher 分组 | 提问、权限、回合完成、会话结束 | — |

## 5. 六个坑（都踩过，按踩到的顺序）

### 5.1 Codex 的 payload 在 argv，不在 stdin

```toml
notify = ["/bin/bash", "/Users/you/.codex/hooks/betterfocus-notify.sh"]
```

Codex 把事件 JSON 作为**单个命令行参数**传进去。两处必须配合：

1. 启动器要 `exec "$PYTHON" hook.py "$@"`（少写 `"$@"`，payload 直接丢）；
2. Python 侧 `EVENT_STYLE == "codex"` 时**绝不能读 stdin**——那里没有数据，
   `json.load(sys.stdin)` 会一直等 EOF，把宿主的终端卡住。

`main()` 里因此先按方言分流再取 payload（`read_payload()`），不是先读 stdin。

### 5.2 TOML 没有「只加一条」的入口

Codex 的 `notify` 是**单值键**，重复即报错；Kimi 的 `[[hooks]]` 是数组表。
用 TOML 库解析后重写会把用户的注释、顺序、行内表全部改排，风险大于收益。

做法（`ManagedTOML`）：只在文件尾部维护一段注释界标包起来的区块，
界标之外一个字节不碰；卸载 = 删区块。

```toml
# >>> betterfocus (managed block, do not edit) >>>
notify = ["/bin/bash", "/Users/you/.codex/hooks/betterfocus-notify.sh"]
# <<< betterfocus <<<
```

**冲突检测**：界标外已有 `notify =` 时**放弃安装并报错**，绝不覆盖别人的通知链
（TOML 不允许重复键，硬加会让整份 config.toml 加载失败）。

### 5.3 Kimi 的 `[[hooks]]` 只认 4 个字段

`event / matcher / command / timeout`，多写任何一个整份配置都加载失败。
所以不能像 JSON 那边塞 `_betterfocus_marker` 自定义字段——只能靠 `command`
里是否含 `betterfocus-notify.sh` 认自己的条目。另外 Kimi 的 `timeout` 上限是 600s，
`agentWaitLimit + 60` 可能超，必须 clamp。

### 5.4 Trae 的 `Notification` matcher 匹配的是 `notification_type`

不是工具名。写成 `Bash` 这类工具名 → 权限提醒**永远不触发**且没有任何报错。
应写 `permission_prompt`。

### 5.5 同一事件可能被注册两次（Trae 会读 `~/.claude` 的 hooks）

Trae 文档明确「同时启用 Claude Code Hook 和 TRAE Hook 时会合并执行」。
两套配置都在，同一个 `AskUserQuestion` 会被两条脚本各处理一次 → 弹两张卡片。

解决：`claim()` 短命占位文件（`answers/.claim_<session>_<tool_use_id>`），先到先得，
后到的**安静退出**，把决定权留给先到的那条。20 秒过期，不会挡住下一次提问。

### 5.6 Qoder CN 与 Qoder 是同一套代码

`~/.qoder-cn` 与 `~/.qoder` 结构完全一致，识别逻辑也一样。用
`export BETTERFOCUS_VARIANT=cn` + 一张映射表把结果换到 `_cn` 命名空间：

```
qoder → qoder_cn    qoder_ide → qoder_cn_ide    qoder_cli → qoder_cn_cli
```

这样 IDE 内置 / CLI / 插件三种形态依然各自可辨，不会因为「一律改成 qoder_cn」
而丢掉 IDE 与 CLI 的区别。

### 5.7 host 会「冒名」：祖先链可能停在别人身上

CLI 侧已经处理了（认不出终端只写产品名），但 **GUI 宿主同样会中招**：
实测在 WorkBuddy 的 shell 里手动跑 Trae CN 的 hook 脚本，`host_app()` 走到的
最外层 `.app` 是 WorkBuddy，于是卡片写成「WorkBuddy 回复完成」、图标也画成
WorkBuddy——产品身份（hook 里编译期写入的 `PROVIDER`）与宿主身份（`host`）打架。

规则：**名字和图标必须同源，且都受 provider 校验**。

```swift
// 名字：bundle 明确属于另一个应用家族 → 只写产品名
// 图标：同样判定，命中时改用产品自己的 bundle 找图标
static func iconIdentity(provider:hostName:bundleID:) -> (name: String?, bundle: String?)
```

两个例外不能误伤：

- **JetBrains 插件**必须保留 `host.name`（否则 "IntelliJ IDEA" 退化成 "Qoder"）。
- **CLI 宿主**永远用终端身份（`Claude Code（Warp）` + Warp 图标），不参与产品校验。

校验只看「bundle 是否登记在别的 provider 家族里」（`IDELauncher.group(for:)`），
认不出的第三方 bundle 不做判断——否则会把 VS Code 内置终端里的 OpenCode
误判成冒名。

## 6. 只装在本机已有的宿主上

给没装的宿主写配置，只会在人家那里留一堆没人读的脚本。安装器统一遵循：

```swift
if InstallerPaths.hostDirectoryExists(dir) { install(...) }
```

例外：Kimi 在「两个配置目录都没有、但 `/Applications/Kimi.app` 存在」时也会写
`~/.kimi-code/config.toml`（该文件在 CLI 未安装时完全惰性）；Codex / Trae 国际版
目录不存在则跳过。

## 7. 验证方式

- 单元测试：`Tests/BetterFocusIDETests/HostAdapterTests.swift`
  - 合并幂等 / 只删自己的分组 / 别人的 hook 不被误删
  - TOML 区块插入→替换→移除回路、外来键冲突检测
  - Kimi 只出现 4 个合法字段、timeout ≤ 600
  - 六份 Python 正文都能 `py_compile`
  - Codex 方言分支必须早于 stdin 读取
  - `Qoder CLI（Warp）` 标注、CLI 跳转目标是终端、CLI 分类
  - host 冒名防护：名字与图标同源（HostAdapterTests 共 18 条，全量 55 条）
- 实机：把真实报文喂给安装后的脚本，看日志里
  `socket: event=turn_finished provider=<宿主>` 与历史里的来源名。
  五个宿主实测均通（claude_code / codex / trae_cn / kimi / qoder_cn_cli）。

## 8. 已知遗留

- **「第二条通知起主线程卡死」未能复现**。现象：第一条通知正常展开并在 5s 后收起，
  第二条展开后不再有 `animateTo ... expanded=false`，之后 socket 事件只进日志、
  不写历史。当时代码里混着并行会话未提交的通知/悬停改动。
  改用 `git worktree` 单独构建（HEAD + 本次适配）后，间隔 8s 连发两条
  `turn_finished` 再补一条 `permission_notice`，三条都正常写进历史，未复现。
  结论：疑似来自那批未提交改动，需在其落地后回归一次再定性。
