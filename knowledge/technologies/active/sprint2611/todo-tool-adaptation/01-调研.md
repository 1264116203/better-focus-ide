# Todo 类工具在各宿主的支持度与可观测性（调研）

日期：2026-11-05
范围：BetterFocusIDE 已适配的 8 类宿主（Qoder / Qoder CN / OpenCode / Cursor /
WorkBuddy / Claude Code / Trae / Kimi / Codex），看它们各自的「待办清单（todo）」
工具叫什么、能不能被 hook 抓到、payload 长什么样。

---

## 0. 一句话结论

**「支持 TodoWrite」和「我们能收到 todo 事件」是两件不同的事。**

- 有 todo 类工具的宿主：**7 类**（Codex 的 `update_plan` 语义接近但不是 todo）
- 今天能把 todo 事件稳定送进 socket 的：**只有 Qoder 系、OpenCode v1、Kimi**
- Claude Code 要从 `TodoWrite` **改挂到 `TaskCreate|TaskUpdate`** 才收得到
- Cursor / Trae **有工具但 hook 不暴露**（枚举表里没有它）
- Codex **只有回合回调**，拿不到过程态

---

## 1. 先分清两个正交问题

做适配时最容易在这里踩空：**工具层**（宿主给模型什么工具）与**观测层**
（宿主会不会为这次工具调用触发 hook）不是一回事，两者可以独立缺失。

| | 工具有 | 工具没有 |
|---|---|---|
| **hook 能看到** | Qoder、OpenCode v1、Kimi、Claude Code(new) | — |
| **hook 看不到** | Cursor、Trae、Codex、OpenCode v2 | — |

名字还分三套血统，不能按「Todos」一个词去匹配：

| 血统 | 工具名 | 宿主 |
|---|---|---|
| Claude Code 系 | `TodoWrite` → 新一代 `TaskCreate/TaskUpdate/TaskList/TaskGet` | Claude Code、Qoder、Trae、Cursor、WorkBuddy |
| OpenCode 系 | `todowrite` / `todoread` | OpenCode v1 |
| 自成一派 | `SetTodoList`（Kimi）、`update_plan`（Codex） | Kimi、Codex |

## 2. 工具层矩阵

| 宿主 | 工具名 | 状态枚举 | 语义 | 备注 |
|---|---|---|---|---|
| Qoder / Qoder CN / JetBrains 插件 | `todo_write`（原生）↔ `TodoWrite`（兼容名） | pending / in_progress / completed | 整表覆盖 | 官方 hook 文档给了完整映射表 |
| OpenCode v1 | `todowrite`（+`todoread`） | pending / in_progress / completed / cancelled | 整表覆盖，`[]` 清空 | 上限 100 条 × 500 字 |
| OpenCode v2 | — | — | — | **整组 todo 工具被删**，含 `session.todo()` 与 `todo.updated` 事件 |
| Claude Code | `TodoWrite`；新模型为 `TaskCreate`+`TaskUpdate`+`TaskGet`+`TaskList` | pending / in_progress / completed / cancelled | 覆盖 → 逐条 UPSERT | v2.1.233 起默认关闭，见 §4.3 |
| WorkBuddy | `TaskCreate` / `TaskUpdate` / `TaskGet` / `TaskList` | pending / in_progress / completed / deleted | 逐条 UPSERT | 本会话工具集实测，无 `TodoWrite` |
| Cursor | `todo_write` | pending / in_progress / completed / cancelled | 覆盖，支持 `merge: true` 增量 | Agent Prompt 2.0 |
| Trae / Trae CN | `TodoWrite` | 同 Claude | 整表覆盖 | 子智能体工具表、系统提示词均列出 |
| Kimi Code CLI | `SetTodoList` | pending / in_progress / **done** | 覆盖；省略参数=查询，`[]`=清空 | 注意是 `done` 不是 `completed` |
| Codex CLI | `update_plan` | steps + 完成状态 | 步骤列表 | v0.152.0 起默认关闭 |

## 3. 观测层矩阵（决定能不能做卡片）

| 宿主 | hook 机制 | 能否拿到 todo 调用 | 该用的 matcher |
|---|---|---|---|
| Qoder / Qoder CN | `PreToolUse` / `PostToolUse` / `PermissionRequest` | ✅ | `TodoWrite` 或 `todo_write`（内部自动映射） |
| OpenCode | JS 插件 `tool.execute.before/after` | ✅ | 按 `input.tool` 判断，无需 matcher |
| Claude Code | `PreToolUse` / `PostToolUse` | ✅ 但要用新名字 | `TodoWrite` **已失效** → `TaskCreate\|TaskUpdate` |
| Kimi | `[[hooks]]` 的 `PreToolUse` | ✅ | `SetTodoList` |
| WorkBuddy | `~/.workbuddy/settings.json` hooks（matcher 是正则） | ⚠️ 待实测 | 理论可挂 `TaskCreate\|TaskUpdate` |
| Cursor | `preToolUse` / `postToolUse` | ❌ | tool_name 只覆盖 6 类，无 todo 位 |
| Trae / Trae CN | `PreToolUse` / `PostToolUse` | ❌ | tool_name 是**枚举表**，无 TodoWrite |
| Codex | `notify`（外部程序） | ❌ | 只有回合完成 |

## 4. 逐宿主细节

### 4.1 Qoder / Qoder CN（唯一官方明说「两套名字等价」的）

Qoder IDE 同时维护原生工具名与 Claude Code 兼容名，hook 文档原话：
「配置 Hook 时可使用任意一套，插件内部会统一映射后执行匹配」，并给出表格：

```
todo_write     ↔  TodoWrite      写入 TODO
run_in_terminal ↔ Bash           执行 shell 命令
read_file      ↔ Read            读取文件
create_file    ↔ Write           创建/写入文件
search_replace ↔ Edit            编辑文件
Agent          ↔ Task            启动子代理
```

由此得两条结论：

- matcher 写 `TodoWrite` 或 `todo_write` **都能命中**，不必为两套名字各注册一份
- IDE 里 payload 的 `tool_name` 可能是原生名，**归一化时要两个名字都认**

CLI 是 Claude Code 血统，原生就是 `TodoWrite`；Qoder CN 与 Qoder 同一套代码，
只是靠 `BETTERFOCUS_VARIANT=cn` 换命名空间（见 `cli-host-adaptation/01-适配经验.md`
§5.6），所以 `qoder_cn*` 三个身份同样适用本行结论。

**未确认**：`todo_write` 的 `tool_input` 字段实测值（是 `content` 还是带
`activeForm`）。接入前先抓一次真实报文。

### 4.2 OpenCode（版本分化最严重的一个）

- **v1**：`todowrite` + `todoread`，参数
  `{todos:[{id, content, status, priority}]}`，status 四值含 `cancelled`；
  整表替换语义，传 `{"todos":[]}` 清空；默认对 General 子代理关闭。
- **v2**：整组 todo 工具**被删除**——`todowrite`/`todoread` 不在 host bundle 里，
  `session.todo()`、`Todo` 类型、`todo.updated` 事件一并消失，只剩下一张没人用的
  todo 存储表。社区靠第三方插件 `opencode-todolist` 把工具补回来。

对插件侧的影响：

- **不要依赖任何 todo 专用 API 或事件**，只认 `tool.execute.before` 的 `input.tool`。
  v2 没有专用事件，todo 只能当「消息流上的一个工具调用」来读。
- **不要硬编码太多工具名**。v2 除了删 todo 还做了重命名：
  `bash → shell`、`task → subagent`、`patch → apply_patch`，文件类参数
  `filePath → path`。今天是 `todowrite`，明天可能就是别的。
- 顺带一个现成的坑：v2 里 `apply_patch` 的工具名是 `apply_patch` 而不是 `patch`，
  官方文档专门写了「在 `tool.execute.before/after` 里要判 `input.tool === "apply_patch"`」。
  我们现有插件如果按 `patch` 判，v2 上是静默失效的。

### 4.3 Claude Code（`TodoWrite` 已经默认消失）

v2.1.233（2026-08-14）变更：**在 Opus 4.8 / Sonnet 5 / Fable 5 / Mythos 5 及更新
模型上，`TodoWrite` 与 `TaskCreate`/`TaskGet`/`TaskUpdate`/`TaskList` 不再默认提供**，
需要 `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` 才恢复；老模型不受影响。

由此产生一个**静默失效**风险：matcher 写 `TodoWrite` 在当前版本是 no-op——不报错、
不告警、只是永远不触发。当前活跃名是 `TaskCreate|TaskUpdate`（matcher 里纯字母数字
会被当成精确串或 `|` 列表，**不是正则**，所以 `Task` 匹配不到 `TaskCreate`）。

V2 与 V1 的语义差：V1 是「整表传一次」，V2 是「逐条 `TaskCreate` 拿 id，再
`TaskUpdate(task_id, status)`」。归一化时必须走 UPSERT，不能整表覆盖——否则每来
一条更新就会把之前那些任务全冲掉。

### 4.4 WorkBuddy

本会话工具集实测：`TaskCreate` / `TaskUpdate` / `TaskGet` / `TaskList`，
外加 `TaskOutput` / `TaskStop`；**没有 `TodoWrite`**。与 Claude Code 的 V2 演进同构，
也印证了 CodeBuddy 血统跟随 Claude Code 的判断。

hook 侧：`~/.workbuddy/settings.json` 的 `matcher` 是正则匹配工具名（我们现已用它挂
`AskUserQuestion` 与 `permission_prompt`），所以理论上挂 `TaskCreate|TaskUpdate`
是可行的——**但没实测过它会不会为 Task* 触发 `PreToolUse`**。这是目前最大的未知项。

历史包袱：老版 CodeBuddy Code 文档里还有 `todo_write → TodoWrite` 的桥接映射，
说明曾经存在 `TodoWrite`。写适配代码时不要把「WorkBuddy 一定没有 TodoWrite」
当成永久事实，两个名字都认最稳。

### 4.5 Kimi Code CLI（名字不同，语义最干净）

`SetTodoList`（`kimi_cli.tools.todo:SetTodoList`），参数
`{todos:[{title, status}]}`，status 是 `pending | in_progress | done`。
三种用法：传数组=覆盖、省略 `todos`=查询当前列表、传 `[]`=清空。

配置层面我们只写四个字段（`event / matcher / command / timeout`，多写一个整份
toml 加载失败），所以接入只是多一组 `[[hooks]]`，matcher 写 `SetTodoList`。

**字段名差异**：Kimi 用 `title`、状态叫 `done`；Claude 系用 `content`、
状态叫 `completed`。这个差异必须在归一化层吃掉，不能泄漏到 UI。

### 4.6 Cursor（有工具，hook 拿不到）

工具有：Agent Prompt 2.0 里的 `todo_write`，四状态，支持 `merge: true` 增量合并。
用户侧的体感确实存在（Plan 模式的任务清单就是它）。

但 hook 侧只有 6 个 tool_name：`Shell`、`Read`、`Write`、`Grep`、`Delete`、`Task`，
外加 `MCP:<tool_name>`。官方对 Claude 名的重写表是
`Bash → Shell`、`Edit/Write → Write`、`Task → Task`、`Glob` 直接丢弃——
**根本没有 todo 的映射位**。社区 issue 里也有同类反馈（`AskUserQuestion` 等 Claude
matcher 在 Cursor 上永不触发的清单，官方逐条确认「没有对应 hook」）。

结论：现阶段拿不到。要展示 todo，只能降级——读 hook 入参里的 `transcript_path`
解析对话记录，或者干脆不做。

实测方法（30 分钟能出结论）：`preToolUse` 的 matcher 写 `*`，脚本里把
`hook_event_name` + `tool_name` 打到日志，跑一个多步任务，看有没有
`TodoWrite` / `todo_write` 冒出来。文档用的是 "Values **include** ..." 非穷举措辞，
值得亲自否一次。

### 4.7 Trae / Trae CN（同 Cursor 命运，但证据更硬）

工具有：文档「子智能体（Subagent）」页的可用工具表里明确列了
`TodoWrite — 管理任务清单`；系统提示词里也有它。对话界面会显示任务清单。

hook 侧：官方「PreToolUse 和 PostToolUse 事件支持的工具」是**枚举表**——
`Read / Write / Edit / Glob / Grep / LS / RunCommand / WebSearch / WebFetch /
AskUserQuestion / Skill / mcp__*`，**没有 TodoWrite**，也没有 `TaskCreate` /
`TaskUpdate`。这不是措辞含糊，是穷举。

本机 `Trae.app` 的 `libai_agent.dylib` 把 hook 工具适配拆成
`tool_compatible/{read,write,search,web,mcp,ask_user_question,apply_patch}.rs`，
没有待办适配。`todo_write.rs` 只存在于工具实现，不进 hook。

**2026-11-07 实测：进度卡不会出现。** 安装器因此不登记 `PostToolUse`。
补挂 matcher 也收不到事件。（另外 Trae 没有 `SessionEnd`，这已经在
`cli-host-adaptation` 里记过。）

### 4.8 Codex CLI（结构性缺失）

`update_plan`（steps + 完成状态，TUI 有 plan 视图），但 v0.152.0（2026-09）起
默认关闭，要 `[tools.update_plan] enabled = true` 才回来。

更关键是：Codex 只有 `notify` 一个外部回调，payload 走 argv、时机是「回合完成」，
**没有 PreToolUse 这类过程事件**。所以即便用户开了 `update_plan`，我们也只能在
回合结束时知道「他刚才可能改过计划」，做不成实时卡片。

## 5. 归一化数据模型

```swift
struct TodoItem {
    let id: String          // 宿主没给 id 时用 content 哈希兜底
    var content: String     // Kimi 的 title 映射到这里
    var status: TodoStatus  // pending | inProgress | completed | cancelled
}
```

两条写入语义必须分开处理，不能只留一条：

| 语义 | 宿主 | 处理 |
|---|---|---|
| **整表覆盖** | Qoder / Trae / Cursor / Claude `TodoWrite` / Kimi / OpenCode v1 | 直接替换本地列表；空数组 = 清空 |
| **逐条 UPSERT** | Claude `TaskCreate`+`TaskUpdate` / WorkBuddy `Task*` | 按 taskId 合并；`TaskList` 兜底做全量校正 |

状态映射：

```
pending                     → pending
in_progress / in-progress   → inProgress
completed / done            → completed
cancelled / deleted         → 从列表移除（或置灰，按 UI 口径定）
```

**注意**：`in-progress`（连字符）这种历史脏值只在旧 SDK 里出现过，仍建议归一化层
同时接受连字符与下划线两种写法。

## 6. 落地顺序建议

1. **Qoder 系（含 CN）** —— 唯一官方给了工具名映射表、事件又齐全的，先做。收益/成本比最高。
2. **OpenCode v1** —— 插件已经在手，加一个 `input.tool === "todowrite"` 分支即可。
   同时把 v2 的重命名问题一并处理（`shell`/`subagent`/`apply_patch`）。
3. **Kimi** —— 加一组 `[[hooks]]` + 别名映射，成本最低的一档。
4. **Claude Code** —— 双 matcher 兜底（`TodoWrite` **和** `TaskCreate|TaskUpdate`），
   并把 V2 的 UPSERT 语义做进控制器；否则新模型用户会看到「卡片永远不出现」。
5. **WorkBuddy** —— 先实测 hooks 是否对 `Task*` 触发，再决定做不做。
6. **Cursor / Trae / Codex** —— 不做；或只做 transcript 降级方案，
   宁可不展示，也别做一个永远不弹的功能。
