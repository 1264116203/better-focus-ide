# ss-analysis-split — 需求分解引擎

**阶段**: analysis | **独立可用**: 不推荐独立调用 | **profile**: basic/enhanced

## 前置条件
- 有 `intake.md`（已澄清的范围与约束）。
- 用户已提供 Epic/Story 列表（标题 + 描述 + AC）。

## 配置加载
执行前**必须**使用 Read 工具读取 `.qoder/wf-dev.yaml`，提取以下字段：
- `workflow_dir.active` → 产物写入路径
- `slug.*` → slug 格式校验（pattern/min_length/max_length）

工作流模式下，**PRD_DIR**（原始 PRD 文件所在目录）由编排器通过上下文传入；独立调用时由用户在 prompt 中给出。未完成配置加载不得开始执行。

## 输入
- `--slug <epic-slug>`
- 工作流模式下自动读取 `PRD_DIR/processing-state/` 下的 intake（逻辑名 `intake.md`，resolver 后为 `01-intake.md`）；独立调用时由用户 prompt 给出 Epic/Story 信息

## 执行步骤（三阶段拆分法）

### 第一阶段：业务功能一级拆分

1. 从 intake.md + 用户提供的 Story 列表中识别**独立可交付的业务功能单元**。
2. 拆分判断维度：
   - 业务活动独立性（能否独立上线、独立验收）
   - 用户角色/场景差异
   - 系统边界（不同服务/模块）
   - 上线时间差异（分阶段交付）
3. 每个功能单元产出：标题、简述、覆盖的原始 Story ID 列表。

### 第二阶段：技术层二级拆分（按需）

4. 对每个一级功能单元，评估是否需要进一步拆分：
   - 涉及 ≥3 架构层 → 考虑按层拆分（BE/FE/数据迁移）
   - 含独立基础设施变更（新表、新中间件）→ 考虑独立拆出
   - 若功能单元本身已满足 Mode B 条件（仅改已有代码 / ≤2 层 / ≤200 行 / 无正式 PRD）→ 不再拆分
5. 二级拆分项继承父项的业务上下文，标注所属一级功能。

### 第三阶段：Mode A/B 评估 + 排序

6. 对每个最终拆分项，用 Mode A 条件逐项打分：
   - [ ] 新建 DB 表
   - [ ] 新建模块
   - [ ] 涉及 ≥3 个架构层
   - [ ] 新增跨层 API
   - [ ] 新增领域实体
   - [ ] 有正式 PRD
   - [ ] 预估变更 >200 行
   - 满足任意 **2 项** → 推荐 `wf-feature-large`
   - Mode B 条件全部满足 → 推荐 `wf-feature-small`
   - 灰色地带（不满足 A 且不满足 B）→ 默认推荐 `wf-feature-small`，并注明可升级到 large 的条件
7. 为每项生成：
   - 建议 slug（kebab-case，符合 `slug.*` 配置校验）
   - 预估规模（S: ≤100 行 / M: 101-200 行 / L: 201-500 行 / XL: >500 行）
   - GWT 验收标准（从原始 AC 提炼，每项至少 2 条）
   - 涉及层标注（BE/FE/DB/共享）
   - **接口概要清单**：从 PRD 提取该拆分项涉及的接口，每个接口含：接口名称、调用方向（如 APP→后端）、协议类型（HTTP/MQ）、入参关键字段、出参关键字段、处理逻辑摘要
   - **数据模型变更**：新增表/修改表，含表名、关键字段、数据类型、约束、关联关系；修改表标注变更内容和影响范围
   - **状态机定义**（如有状态流转）：状态枚举值、转换条件、触发动作、前置/后置条件
   - **关键业务规则**：从 PRD 提取的特殊场景处理规则、边界条件、降级方案
   - **模块交互关系**：该系统/模块与其他模块的调用关系（谁调用谁、通过什么方式）
8. 分析依赖关系（数据依赖、API 依赖、共享组件依赖），排出执行顺序，标注可并行组。
9. 验证依赖关系无环（拓扑排序可行）。

## 输出
- 逻辑名 `split-result.md`（写入 `PRD_DIR/processing-state/`，编排器 resolver 为 `02-split-result.md`），结构如下：

```
# 拆分结果

## 拆分项清单
（每项含：ID、标题、简述、推荐工作流、推荐理由、建议 slug、规模、涉及层、GWT 验收标准、覆盖 Story ID）

## 拆分项详情（每项重复以下结构）

### WF-N: <标题>
#### 接口概要清单
| 接口名称 | 调用方向 | 协议 | 入参关键字段 | 出参关键字段 | 处理逻辑摘要 |

#### 数据模型变更
- 新增表：表名、关键字段、数据类型、约束
- 修改表：表名、变更内容、影响范围
- 表关系说明

#### 状态机定义（如有）
- 状态枚举：0=默认, 1=进行中, ...
- 转换规则：状态A → 状态B，触发条件，前置/后置条件

#### 关键业务规则
- 规则1：描述 + 边界条件
- 规则2：描述 + 降级方案

#### 模块交互关系
- 模块A → 模块B：调用方式（HTTP/MQ/共享组件）

## 依赖关系
（邻接表形式 + 可并行组标注 + 依赖类型：API依赖/数据依赖/MQ依赖）

## 执行顺序
（拓扑排序后的批次列表）

## 覆盖映射表
（原始 Story ID → 拆分项 ID，确保全覆盖）
```

## 完成标准 (Done)
- 每个拆分项可独立交付、有明确 GWT 验收标准（≥2 条）。
- 依赖关系无环（拓扑排序验证）。
- 覆盖原始 Epic 全部 Story（覆盖映射表无遗漏）。
- 每项有明确的 wf-large/small 推荐及逐项打分理由。
- 建议 slug 符合 `slug.*` 配置校验。

## basic vs enhanced
- basic：一级拆分为主，二级拆分仅在明显必要时（≥3 层或新表）执行；依赖关系用简单有序列表；省略风险项。
- enhanced：完整两阶段拆分 + 依赖图（mermaid graph TD）+ 并行组标注 + 风险项识别（技术风险/依赖风险/规模风险）。

## 异常处理
- 某功能单元无法拆到满足 Mode B 条件且 Mode A 条件也不明确 → 标 WARNING，建议人工判断，继续处理其余项。
- 原始 Story 信息不足以判断规模 → 标 BLOCKING，回退用户补充。
- 依赖关系检测到环 → 标 BLOCKING，列出环路径，要求用户确认优先级打破环。
