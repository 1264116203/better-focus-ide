## 拆分强制约束（铁律）

> **背景**：阶段 7（ss-tdd-cycle）的任务默认由主会话**串行**执行，每个 `实现` 类 task 需经历「红→绿→重构」完整 TDD 循环。任务数过多直接导致阶段 7 耗时线性增长，因此必须控制总数、保证每个任务功能闭环。

### 约束 1：任务总数上限（实现 + 配置）
- 进入阶段 7（ss-tdd-cycle）执行的 **任务总数上限为 3 个**（`实现` 类 + `配置` 类合计）。
- 若初步拆分超出 3 个，**必须**按下方「合并策略」进行合并，直至 ≤ 3。
- `配置` 类任务虽不进入 TDD 循环，但仍计入总数上限（避免阶段 7 任务膨胀）。

### 约束 2：功能边界完整性（高内聚）
- 每个任务必须具备**清晰、独立的功能边界**，能独立实现与测试。
- **禁止**将同一业务逻辑或强耦合代码强行拆碎——每个任务应代表一个**完整的业务子特性或独立功能模块**。
- 判断标准：若两个任务需要频繁修改同一文件/同一方法，则应合并为一个任务。
- 每个任务的验收标准必须覆盖其完整功能闭环，不得出现"半功能"任务。

### 合并策略（约束 1 的执行指南）

#### 归约算法（从 N → ≤ 3 的逐步流程）

当初步拆分产生 N 个 `实现` 类任务（N > 3）时，按以下步骤归约：

**Step 1 — 实体/域分组**：将所有任务按**核心业务实体或领域**归类（如「用户」「订单」「权限」），得到 G 个分组。

**Step 2 — 分组内纵向切片**：每个分组内的任务，按「用户可见的端到端能力」合并为纵向切片（vertical slice）——每个切片应覆盖从数据层到展示层的完整链路，而非按技术层横切。

**Step 3 — 分组间合并**：若 G > 3，按以下规则将分组合并至 ≤ 3：
- 优先合并**存在依赖关系**的分组（如「订单」依赖「用户」→ 合为「用户与订单」）
- 其次合并**共享基础设施**的分组（如共用同一张配置表的两个域）
- 最后按**业务亲缘性**合并（同属一个上层业务模块的分组）

**Step 4 — 复杂度校验**：合并完成后逐项检查复杂度，超过 L 的任务需回退重新划分。

#### 合并方式参考

| 方式 | 适用场景 | 示例 |
|------|---------|------|
| **纵向切片合并** | 同一业务实体的多层实现 | 「用户注册 BE」+「用户注册 FE」→「用户注册（端到端）」 |
| **同模块 CRUD 合一** | 同一实体的增删改查 | 「创建用户」+「查询用户」+「更新」+「删除」→「用户管理 CRUD」 |
| **同域子特性合一** | 同一业务域内的多个子流程 | 「订单创建」+「订单校验」+「状态流转」→「订单生命周期管理」 |
| **基础设施归类** | 纯技术配置/横切关注点 | 「缓存配置」+「日志切面」+「异常处理」→ 合并为 1 个 `配置` 类任务（计入总数上限） |

#### 合并反模式（禁止）

| 反模式 | 原因 |
|--------|------|
| 跨不相关业务域强行合并 | 如「用户管理」+「报表导出」→ 内聚性差，验收标准无法统一 |
| 按技术层横切合并 | 如「所有 BE」+「所有 FE」→ 失去功能闭环，无法独立测试 |
| 为凑数合并无依赖任务 | 仅为了满足 ≤ 3 而合并毫无关联的任务 → 复杂度高且难以并行 |

合并后单个任务复杂度不得超过 **L**。若合并后超过 L，说明合并范围过大，应拆分为 2 个任务并检查总数是否仍 ≤ 3；若反复无法收敛（拆分后 > 3 且合并后 > L），**立即回退 ss-design-tech 复审架构分层**，不得强行推进。

### 拆分自检清单
完成拆分后，必须逐项自检：
1. ✅ 任务总数（`实现` + `配置`）≤ 3？
2. ✅ 每个任务是否代表一个完整的业务子特性（非代码片段/单接口级别）？
3. ✅ 是否存在两个任务频繁修改同一文件/方法的情况？（存在则须合并）
4. ✅ 每个任务是否可独立编写测试并验收？
5. ✅ 合并后每个任务复杂度 ≤ L？（超过则需回退重新划分边界）
6. ✅ 所有 design.md 中的功能点均被某个任务覆盖？（无遗漏）
7. ✅ 并行组内各 task 的文件边界清单无交集？（有交集则调整任务边界或改标注为串行）

未通过自检 → 必须调整拆分方案后重新自检，直至全部通过。

## 执行步骤
1. 将设计拆分为高内聚、功能闭环的任务（遵循上方拆分强制约束）。
2. 为每任务标注：类型、优先级(P0-P3)、依赖、复杂度(S/M/L)、验收标准、涉及层(BE/FE/共享)、状态。
3. 识别可并行任务与联调任务；排出执行顺序；为每个 `实现` task 标注「文件边界清单」（预计涉及/修改的文件集合，含测试文件路径）与并行组归属（供阶段 7 并行前置校验）。
4. 写 `plan.md`（实施策略）+ `tasks.md`（任务表，格式见下方）。

## tasks.md 输出格式

| ID | 任务标题 | 类型 | 优先级 | 依赖 | 复杂度 | 涉及层 | 验收标准 | 状态 |
|----|---------|------|--------|------|--------|--------|---------|------|
| T1 | 用户管理 CRUD（创建/查询/更新/删除 API + 列表页面，含分层类/DDL/映射） | 实现 | P0 | - | L | 共享 | F1 GWT 全通过 | TODO |
| T2 | 用户导入导出（文件上传解析 + 批量导入 + 导出下载） | 实现 | P1 | T1 | L | 共享 | F2 GWT 全通过 | TODO |
| T3 | 权限与审计日志配置 | 配置 | P0 | - | S | BE | 配置加载正常 | TODO |

类型值：`实现`（业务逻辑与分层代码，TDD 阶段逐 task 完成）、`配置`（纯配置/DDL/映射变更，无业务逻辑）。

状态值：`TODO` → `IN_PROGRESS` → `DONE` / `BLOCKED`。

### 执行顺序
1. T3（配置，无依赖）
2. T1（实现，P0 先行；按需先建分层类/DDL/映射）
3. T2（实现，依赖 T1）

## 输出
- `plan.md`、`tasks.md`（含优先级/依赖/复杂度/验收/状态）。
- `plan.md` 含每个 `实现` task 的「文件边界清单」与并行组标注（阶段 7 并行前置校验依据）。

## 完成标准 (Done)
- 每任务可独立交付且有验收标准；依赖关系无环；覆盖 design 全部内容。
- 每个任务已标注类型（实现/配置）；`实现` 类任务均有可测验收标准。
- **任务总数（`实现` + `配置`）≤ 3**（拆分强制约束·约束 1）。
- 每个任务代表完整业务子特性，无"半功能"拆分（拆分强制约束·约束 2）。
- 拆分自检清单 6 项全部通过。

## basic vs enhanced
- basic：单一 tasks.md，省略并行/联调拆分。
- enhanced：plan.md + tasks.md，标注并行组与联调任务，并产出文件边界清单（供阶段 7 并行前置校验）。

## 异常处理
- 任务总数（`实现` + `配置`）> 3 个 → 必须按业务模块合并，不得跳过；合并后仍超限时，回退 ss-design-tech 复审架构分层。
- 任务功能边界模糊或与其他任务强耦合 → 合并为高内聚任务；无法合并说明设计耦合过重，回退 ss-design-tech。
