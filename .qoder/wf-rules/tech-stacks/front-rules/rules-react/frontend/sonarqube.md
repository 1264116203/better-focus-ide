# SonarQube 代码质量规范（React）

## 重要原则
- SonarQube 作为项目代码质量门禁工具之一，用于辅助保障代码的可靠性、可维护性和安全性。
- SonarQube 的治理重点优先放在“新代码”，不要求一次性清理全部历史遗留问题。
- Pull Request 是否可合并，优先以 SonarQube Quality Gate 结果为准。
- 修复 SonarQube 问题时，仍必须遵循项目既有规范：
    - 最小可行改动
    - 先理解上下文再修改
    - 不做无关重构
    - 不顺手修改不相关逻辑
- 不允许为了消除 SonarQube 告警，擅自扩大修改范围或重写稳定模块。

---

## 目标定位
SonarQube 在本项目中的定位如下：
- 不是格式化工具
- 不是纯代码风格工具
- 不是替代 ESLint 的工具
- 是面向代码质量的审计与门禁工具

SonarQube 主要用于关注以下问题：
- 新引入的 Bug
- 新引入的安全问题
- 新引入的代码异味（Code Smells）
- 新引入的重复代码
- 新代码测试覆盖率不足
- 复杂度过高、可维护性过差的实现
- Pull Request 合并前的质量门校验

## 与项目现有规则的关系

### 与 `code-style.md` 的关系
- `code-style.md` 负责日常代码风格、命名、拆分、职责边界规范。
- SonarQube 负责发现可维护性、复杂度、重复逻辑、潜在问题等质量问题。
- 不要把 SonarQube 当作纯风格检查工具使用。

### 与 `testing.md` 的关系
- 测试覆盖率由项目测试产物提供。
- SonarQube 读取测试覆盖率报告并作为质量门条件之一。
- 未生成覆盖率报告时，不得虚假声称 SonarQube 覆盖率已验证。

### 与 `project-structure.md` 的关系
- 目录职责清晰、页面私有逻辑内聚、公共能力合理收口，有助于减少重复代码与复杂度问题。
- 遇到 SonarQube 提示复杂度过高时，优先先检查是否违反了既有目录与组件拆分规范。

### 与变更安全的关系
- SonarQube 问题修复必须服从变更安全原则（见 wf-rules/orchestrator-behavior.md「确认交互约束」）。
- 不允许为了解决单个 SonarQube 告警，擅自重构大范围模块。
- 若问题属于历史遗留代码，可在最终说明中提示，但不要擅自扩大修复范围。

### 与命令执行约束的关系
- 不允许为了接入 SonarQube 擅自安装依赖、联网下载、升级工具。
- 不允许擅自修改 CI 平台配置、服务端配置、账号权限、token 配置。
- 若执行 SonarQube 相关命令受限，只能说明原因并提示开发者处理。

## 治理策略：优先关注新代码
- 本项目采用“新代码优先”的治理策略。
- 每次开发只要求对本次新增或修改的代码负责。
- 不要求因为一个小需求，顺手清理整个老模块的历史问题。
- 若历史代码被本次修改直接触达，则应在最小范围内一并修复与当前改动强相关的问题。
- 若历史问题与当前需求无直接关系，可记录并提示，但不强制在本次任务中处理。

### 新代码的理解方式
- 新代码指最近新增或修改的代码。
- 在 Pull Request 分析中，新代码应理解为当前 PR 相对于目标分支产生的变更部分。
- Pull Request 质量门仅关注适用于新代码的质量门条件。

## Quality Gate 使用原则
- 项目必须配置 Quality Gate。
- Pull Request 合并前必须检查 Quality Gate 状态。
- Quality Gate 不通过时，默认视为当前改动未达到可合并标准。
- 不允许绕过 Quality Gate 直接把不达标代码视为“已完成”。
- 若确需例外处理，必须由项目负责人明确决定，不由执行者自行判断。

### Quality Gate 推荐方向
本项目推荐优先基于“新代码”设置质量门条件，不强制对“整体代码”一开始就设置过重门槛。

推荐优先关注以下维度：
- New Bugs
- New Vulnerabilities
- New Security Hotspots Reviewed
- Coverage on New Code
- Duplicated Lines on New Code
- Maintainability / Reliability / Security on New Code

### 推荐门槛（建议值，可由团队按实际调整）
- New Bugs = 0
- New Vulnerabilities = 0
- New Security Hotspots Reviewed = 100%
- Coverage on New Code：以 `.qoder/wf-dev.yaml` `coverage.new_code` 为准（默认 100%），SonarQube 侧阈值与之一致
- Duplicated Lines on New Code <= 3%
- Maintainability Rating on New Code = A
- Reliability Rating on New Code = A
- Security Rating on New Code = A

### 落地原则
- 初期若项目历史包袱较重，可先启用较少的新代码门槛。
- 不建议一开始就对整体代码设置过严门禁，避免阻塞正常业务开发。
- 应逐步提升要求，而不是一次性把所有指标拉满。

---

## Quality Profile 使用原则
- 项目必须绑定明确的 Quality Profile。
- JavaScript / TypeScript 规则集应基于团队统一质量要求进行管理。
- 不允许每个项目成员按个人偏好随意解释 SonarQube 规则。
- 若项目已有统一 Profile，则必须优先服从项目既有配置。
- 若需定制规则，应由项目或团队统一调整，不应在任务执行中临时改变。

### 规则调整原则
- 规则调整应以团队统一标准为准。
- 不允许因为某一条告警难改，就临时关闭规则来规避问题。
- 若某类规则与项目现有架构明显冲突，应先评估：
    - 是否为规则误报
    - 是否为历史架构原因
    - 是否需要统一调整实现方式
- 不允许个人绕开团队质量标准。

---

## Pull Request 分析规范
- Pull Request 必须接入 SonarQube 分析。
- 每次 PR 创建后、以及 PR 分支有新提交后，应触发新的分析。
- PR 分析应作为代码评审前置质量参考。
- PR 装饰信息如已接入代码平台，应优先在 PR 界面查看 SonarQube 问题摘要。
- PR 不通过时，优先处理本次改动引入的问题。

### PR 分析时的基本要求
- 重点关注本次改动新增的问题
- 不要求清理整个仓库的历史问题
- 优先修复：
    - 新 Bug
    - 新漏洞
    - 新增高严重级别问题
    - 新增重复代码
    - 新增覆盖率不足
- 对于历史遗留问题，仅在本次修改直接关联时再评估是否顺带处理

## 与 ESLint 的职责边界
- ESLint 负责：
    - 基础语法问题
    - hooks 规则
    - import 规范
    - JSX 书写习惯
    - 常见静态风格问题
- SonarQube 负责：
    - 可维护性问题
    - 圈复杂度 / 认知复杂度
    - 重复代码
    - 潜在 Bug
    - 安全风险
    - 覆盖率与质量门

### 处理原则
- 同一问题若 ESLint 已能明确治理，优先按 ESLint 规范处理。
- SonarQube 不用于替代项目的基础编码规范。
- 两者结论冲突时，优先结合项目既有规范和实际业务上下文判断，不做机械处理。

## 针对本项目目录结构的扫描建议

### 建议纳入主要分析范围的目录
- `src/components/`
- `src/layouts/`
- `src/pages/`
- `src/router/`
- `src/utils/`
- `src/hooks/`
- `src/services/`
- `src/App.jsx`
- `src/main.jsx`
- `src/theme.js`
- `src/context.js`
- `src/reducer.js`

### 建议排除的目录或内容
- `dist/`
- `coverage/`
- `public/`
- `env/`
- `node_modules/`
- `src/mock/`
- 自动生成文件
- 测试报告产物
- 构建产物
- 第三方复制代码
- 明确非业务维护源码的静态资源

### 排除原则
- 不分析构建结果
- 不分析静态资源目录
- 不分析本地 mock 数据目录
- 不分析外部生成代码
- 不把非业务源码目录纳入主质量评价范围

## 测试覆盖率规范
- SonarQube 使用项目测试产出的覆盖率报告进行覆盖率统计。
- 覆盖率数据必须来源真实测试执行结果，不允许伪造。
- 若项目未产出覆盖率报告，则应明确说明“未接入覆盖率统计”，不能默认判定覆盖率通过。
- 新代码覆盖率应优先纳入质量门。
- 小改动若未直接适合编写测试，可在最终说明中明确说明原因，但不能把“未写测试”表述成“已验证覆盖率”。

### 覆盖率治理原则
- 优先保证核心逻辑、公共组件、公共 hooks、请求处理逻辑、权限逻辑的测试覆盖。
- 简单展示层不要求机械堆测试。
- 不鼓励为追覆盖率而写无意义测试。
- 覆盖率必须服务于真实质量保障，而不是形式化数字达标。

---

## 重复代码治理原则
- SonarQube 提示重复代码时，优先判断是否属于真实重复业务实现。
- 若为页面私有的小范围重复，先评估是否值得抽离。
- 不允许为了降低重复率，强行把尚不稳定的页面逻辑提前抽成全局通用组件。
- 只有在重复逻辑具备明确通用性、边界稳定时，才考虑抽象复用。
- 修复重复代码问题时，必须遵循目录结构规范和最小改动原则。

---

## 复杂度治理原则
- SonarQube 提示复杂度过高时，优先检查：
    - 是否页面主文件承担过多职责
    - 是否组件未按规范拆分
    - 是否 hooks 混入过多无关逻辑
    - 是否把配置、请求、格式化、视图逻辑混写
- 修复方式优先考虑：
    - 组件拆分
    - hooks 拆分
    - 配置抽离
    - 工具函数抽离
    - 条件分支收敛
- 不允许只为了压复杂度数值，做无意义函数切碎。

## SonarQube 问题处理优先级

### 必须优先处理
- Blocker 问题
- Critical 问题
- 新引入的 Bug
- 新引入的 Vulnerability
- 影响 Quality Gate 的新代码问题
- 本次修改直接引入的高严重级别问题

### 结合上下文处理
- Major 级别问题
- 本次改动触达区域内的旧问题
- 可维护性问题
- 重复代码问题
- 复杂度问题

### 可记录待后续处理
- 与本次需求无关的历史 Minor 问题
- 远离本次改动路径的旧代码异味
- 不影响本次交付的历史低优先级问题

---

## 修复 SonarQube 问题时的变更要求
- 只修与当前需求或当前 PR 强相关的问题
- 不顺手清理整页或整模块的历史告警
- 不擅自改动公共底层，只为让当前页面告警消失
- 若问题位于公共组件、公共 hooks、公共 utils，必须评估所有调用方影响
- 不允许把修告警变成变相重构

### 推荐修复顺序
1. 先修本次新增的高优先级问题
2. 再修影响 Quality Gate 的问题
3. 再评估本次改动直接关联的中优先级问题
4. 历史遗留问题只做记录或最小范围顺带修复

## AI 执行约束
- AI 可以：
    - 编写 SonarQube 规范文档
    - 生成 `sonar-project.properties` 模板
    - 生成 CI 接入建议
    - 根据 SonarQube 问题给出修复方案
    - 在既有项目规则内做最小范围代码调整建议
- AI 不可以：
    - 擅自安装 SonarScanner 或其它依赖
    - 擅自联网下载插件
    - 擅自修改 SonarQube 服务端配置
    - 擅自配置账号、token、Webhook、PR Decoration
    - 在没有真实执行结果的情况下声称已通过 SonarQube 校验

---

## 命令与执行策略
- 若项目本地已具备 SonarQube 扫描能力，可在项目既有命令体系下使用最小必要命令。
- 若本地未具备扫描能力，不允许擅自安装依赖解决。
- 若 CI 已接入 SonarQube，以 CI 结果为准。
- 若本地无法复现 SonarQube 环境，应明确说明限制，不可伪造结论。

### 禁止事项
- 禁止擅自安装 SonarScanner
- 禁止联网下载 SonarQube 插件或依赖
- 禁止伪造扫描结果
- 禁止把未执行的 SonarQube 校验说成已执行
- 禁止为了过 SonarQube 质量门而扩大无关改动范围

---

## 推荐接入方式
本项目推荐 SonarQube 接入顺序如下：

1. 在 SonarQube 服务端创建项目
2. 配置项目的 Quality Profile
3. 配置项目的 Quality Gate
4. 定义 New Code 策略
5. 在 CI 中接入 Pull Request 分析
6. 在 CI 中输出测试覆盖率报告
7. 通过 Quality Gate 控制 PR 合并

### 推荐执行原则
- 优先以 CI 为准
- 本地扫描只作为辅助自检
- 评审时优先看 PR 新代码问题
- 不要求一次性清理所有历史问题

---

## 最终说明要求
当任务涉及 SonarQube 时，最终回复必须明确说明：

- 是否修改了 SonarQube 相关配置文件
- 是否仅补充了规范文档
- 是否实际执行了 SonarQube 相关校验
- 若未执行，原因是什么：
    - 环境缺失
    - 工具缺失
    - token / 服务端未配置
    - CI 未接入
- 如果有 SonarQube 问题，仅说明本次处理了哪些与当前改动直接相关的问题
- 如果存在历史遗留问题，应明确说明未擅自扩大修复范围

---

## 推荐最终表达方式
- 本次仅按新代码治理原则处理与当前改动直接相关的 SonarQube 问题
- 未对无关历史问题做扩大修复
- 未擅自安装 SonarQube 依赖或联网配置服务
- 若未执行 SonarQube 扫描，已明确说明受限原因
- 若已接入 CI，以 Quality Gate 结果作为是否可合并的重要依据
