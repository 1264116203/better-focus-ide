# 前端校验与测试规范（Vue 3）

## 重要原则
- 修改代码后，优先执行与当前改动最相关、最小范围的校验。
- 非必要不执行全量 build。
- 非必要不执行全量测试。
- 校验失败时，必须区分：
  - 代码问题
  - 环境问题
  - 工具缺失
  - 历史遗留问题
- 不要因为一个无关历史问题，误判为本次改动失败。

---

## 校验优先级
每次修改后，按以下顺序选择最小必要校验：

1. 语法级检查
2. 当前改动文件的静态检查
3. 当前页面或模块的最小运行链路检查
4. 与当前改动直接相关的测试
5. 必要时再考虑更大范围校验

---

## 基本校验原则

### 1. 小改动
适用场景：
- 文案调整
- 样式微调
- 小范围模板调整
- 配置项修正

优先校验：
- 语法是否正确
- import 是否正确
- 模板是否可解析
- 核心页面是否能正常渲染

### 2. 中等改动
适用场景：
- 页面局部逻辑修改
- composables 调整
- 表单逻辑修改
- 列表查询、分页、筛选调整
- 弹窗交互调整

优先校验：
- 当前页面主链路
- 相关组件联动
- 状态更新是否正常
- 关键事件是否生效
- 是否产生控制台报错

### 3. 较大改动
适用场景：
- 公共组件修改
- 路由守卫修改
- 权限逻辑修改
- 全局状态修改
- 请求封装修改
- 布局修改

优先校验：
- 直接受影响页面
- 典型调用方
- 权限入口
- 路由跳转链路
- 核心公共交互

---

## 校验内容清单

### 语法检查
修改完成后，优先确认：
- 文件语法是否正确
- 模板标签是否闭合
- `script setup` / `setup` 语法是否正确
- import / export 是否正确
- 变量、函数、组件名是否一致
- 是否存在明显未定义变量

### Vue 3 相关专项检查
- composables 是否在合法上下文中调用
- `ref` / `reactive` / `computed` 使用是否合理
- `watch` / `watchEffect` 依赖是否合理
- 列表渲染是否提供稳定 `key`
- 条件渲染是否存在空值异常
- 组件卸载时是否清理副作用
- 是否存在响应式丢失、解构失效、旧值引用错误等问题
- `props` / `emits` / `defineExpose` 是否与组件协议一致
- `v-model` 绑定是否正确，双向数据流是否符合约定

### 页面交互检查
- 页面是否能正常进入
- 查询是否生效
- 重置是否生效
- 弹窗是否可打开和关闭
- 提交后反馈是否正常
- 表格、表单、分页、筛选是否正常联动
- loading、empty、error 状态是否可用

### 路由与权限检查
涉及路由或权限时，必须检查：
- 路由是否可达
- 重定向是否正常
- 菜单高亮是否正确
- 无权限场景是否符合预期
- 页面标题、面包屑、布局是否正常
- 隐藏页、详情页 `activeMenu` 是否正常
- `route.meta` 驱动的页面行为是否正常

### 请求与数据检查
涉及 `service / request / http` 时，必须检查：
- 请求参数是否正确
- 返回值结构是否匹配当前页面使用方式
- 错误分支是否可处理
- loading 是否正确收口
- 异常时是否影响页面继续使用
- 是否破坏已有接口兼容性

### 公共组件检查
修改公共组件时，必须额外检查：
- 至少一个原有调用方
- 至少一个边界场景
- 默认 `props` 是否兼容
- 样式是否影响其它页面
- 事件回调是否保持兼容
- 插槽行为是否保持兼容

---

## 校验范围控制
- 优先校验当前改动直接影响范围。
- 不要默认执行整个项目所有校验。
- 不要因为追求“保险”而跑全量 build。
- 如果项目测试覆盖不足，应明确说明未覆盖部分，而不是假设一切正常。

---

## 命令执行原则
- 优先使用项目已有命令，不擅自新增命令。
- 不执行依赖安装命令。
- 不执行联网操作。
- 不执行与当前任务无关的全量命令。
- 如需执行命令，优先选择最小范围命令。

---

## 校验失败分类规则

### 代码问题
特征：
- 当前改动文件存在语法错误
- 当前改动逻辑导致运行时报错
- 当前改动导致类型、变量、依赖引用异常
- 当前页面直接不可用

处理要求：
- 优先定位并修复
- 明确指出具体原因和文件位置

### 环境问题
特征：
- 本地缺少运行条件
- 环境变量缺失
- 本地服务依赖未启动
- 非代码本身导致校验无法完成

处理要求：
- 明确说明是环境问题
- 不要误判为代码错误

### 工具缺失
特征：
- lint / test / build 工具不可用
- 命令不存在
- 脚本未配置
- 本地校验链路不完整

处理要求：
- 明确说明工具缺失
- 不要自行安装依赖
- 不要擅自修改项目脚本

### 历史遗留问题
特征：
- 未改动模块本身已有报错
- 老代码已存在 warning / error
- 校验时暴露与本次改动无关的问题

处理要求：
- 明确区分是否与本次改动直接相关
- 可以在总结中提示
- 不要擅自扩大修复范围

---

## 推荐校验策略

### 样式改动
最小校验建议：
- 页面是否正常渲染
- 样式是否生效
- 是否影响相邻模块
- 是否出现布局错位或覆盖问题

### 表单改动
最小校验建议：
- 初始值是否正确
- 输入是否正常
- 校验规则是否生效
- 提交与重置是否正常
- 禁用、只读、必填状态是否正常
- `v-model` 是否与组件值类型一致

### 表格改动
最小校验建议：
- 列是否正常展示
- 列渲染是否正常
- 分页、排序、筛选是否正常
- 空数据态是否正常
- 操作列事件是否正常

### composables 改动
最小校验建议：
- composables 调用位置是否合法
- 返回值结构是否兼容调用方
- 依赖变化是否触发正确
- 是否存在重复请求、重复渲染或状态错乱

### service 改动
最小校验建议：
- 方法名和返回值语义是否一致
- 页面侧消费是否兼容
- 错误处理是否仍然有效
- 是否影响其它调用方

### 路由改动
最小校验建议：
- 路由是否能进入
- 菜单与权限是否正常
- 重定向是否正常
- 页面布局是否正常挂载

### SFC 结构改动
最小校验建议：
- `.vue` 文件模板是否可编译
- `script setup` 是否正常执行
- `props` / `emits` / 插槽是否兼容调用方
- 局部样式是否误伤其它组件

### Pinia 改动
最小校验建议：
- store 初始化是否正常
- action 调用是否正常
- getter / computed 派生数据是否正确
- 是否影响已有依赖页面
- 是否引入共享状态污染

---

## 不建议的行为
- 不要每次修改都跑全量 build。
- 不要每次修改都跑全部测试。
- 不要在没有必要时做全项目联调。
- 不要把未执行的校验说成已执行。
- 不要把无法验证的内容表述成“已确认没问题”。

---

## 推荐表达
- 已执行：当前文件语法检查 / 当前页面最小链路检查
- 未执行全量 build，避免扩大影响范围
- 如存在历史问题，需明确说明与本次改动是否直接相关

---

## Vue 3 项目额外要求

### 单文件组件（SFC）检查
- 模板、脚本、样式三部分修改后，应优先检查当前组件是否仍可正常编译。
- 模板中的条件渲染、列表渲染、插槽渲染应确保不会引发运行时报错。
- 样式变更应确认未通过 `:deep()` 或全局类名污染其它页面。

### Composition API 检查
- `watch`、`watchEffect`、`onMounted`、`onUnmounted` 等副作用逻辑必须检查是否有重复执行或未清理问题。
- `computed` 应只承担派生逻辑，不应在校验中发现副作用混入。
- 解构 `props`、store、reactive 对象时，必须关注响应式是否失效。

### 组件协议检查
- 改动组件后，应确认：
  - `props` 默认值是否兼容
  - `emits` 是否仍符合调用方预期
  - `v-model` 名称和事件是否正确
  - 插槽参数是否保持兼容
  - `defineExpose` 暴露能力是否未被无意破坏

---

## 最终说明要求
当任务涉及校验与测试时，最终回复必须明确说明：
- 本次执行了哪些最小范围校验
- 哪些校验未执行
- 未执行原因是什么：
  - 无必要
  - 环境限制
  - 工具缺失
  - 脚本未配置
- 若出现报错，必须区分：
  - 当前改动导致
  - 历史遗留问题
  - 环境问题
  - 工具问题
- 若未做全量 build / 全量测试，应明确说明是为了控制校验范围，避免扩大影响

---

## 推荐最终表达方式
- 本次已按最小必要原则执行与当前改动直接相关的校验
- 未执行无关全量 build / 全量测试，避免扩大影响范围
- 若存在失败项，已明确区分是代码问题、环境问题、工具缺失还是历史遗留问题
- 未把未执行的校验表述为已完成

## 前端测试环境模式 (test_env)

工作流支持三种前端测试环境模式（mock / real / hybrid），由 AI 按场景确定（见 ss-tdd-cycle 前置条件 test_env），配置模板见 `test-profile-templates.md`。

| 模式 | API 调用 | 浏览器环境 | 测试工具 | 适用场景 |
|------|---------|-----------|---------|---------|
| **mock**（默认） | Vitest vi.mock | happy-dom | Vitest | 日常开发迭代 |
| **real** | 真实 API 调用（需后端服务运行） | Playwright Chromium | Vitest 单测 + Playwright E2E | 发布前验证 |
| **hybrid** | 选择性 Mock（部分端点 mock，部分真实） | happy-dom + 选择性 Playwright | Vitest + 选择性 E2E | 定向集成测试 |

### mock 模式（默认）

当前默认模式，所有 API 调用使用 vi.mock 模拟：

```js
// Vitest
vi.mock('@/api/auth', () => ({
  login: vi.fn().mockResolvedValue({ code: 200, data: { token: 'mock-token' } }),
  getCaptcha: vi.fn().mockResolvedValue({ code: 200, data: { captchaBase64: 'mock' } }),
}))
```

测试命令：`npm run test:unit`（使用 vitest.config.ts，happy-dom 环境）

### real 模式

使用真实后端 API 和 Playwright 浏览器 E2E 测试：

```js
// Playwright E2E 测试（需后端服务运行）
import { test, expect } from '@playwright/test'
test('login with real API', async ({ page }) => {
  await page.goto('http://localhost:5173/login')
  await page.fill('[data-test=phone]', '13800138000')
  await page.click('[data-test=submit]')
  await expect(page).toHaveURL(/\/dashboard/)
})
```

测试命令：`npm run test:e2e`（需先启动后端服务 + 前端 dev server）

**real 模式注意事项：**
- 后端服务必须运行（Spring Boot 或其他）
- 前端 dev server 必须运行（npm run dev）
- Playwright 必须安装（`npm install -D @playwright/test` + `npx playwright install`）
- 必须包含 API 连通性验证 TC 和页面渲染验证 TC

### hybrid 模式

选择性 Mock + 选择性真实 API 调用：

```js
// Vitest 单测：部分 mock
vi.mock('@/api/auth', () => ({
  login: vi.fn().mockResolvedValue({ code: 200, data: { token: 'mock-token' } }), // mock 登录
  getUserInfo: vi.fn(), // 不 mock，使用真实 API（需后端运行）
}))
```

测试命令：`npm run test:hybrid`（Vitest + 选择性真实 API，见 test-profile-templates.md）

### 模式选择原则

- `mock`：日常开发，快速迭代，CI 无外部依赖
- `real`：发布前验证，捕获前后端交互问题（如 API 响应格式不匹配、路由权限问题）
- `hybrid`：定向验证（如验证特定 API 调用但 Mock 登录流程），平衡速度与真实性
- 默认 `mock`（AI 未指定时）
