# Element Plus 使用规范（Vue 3 / Element Plus @2）

## 重要原则
- 涉及 Element Plus 时，优先遵循项目已有封装和使用习惯。
- 优先复用项目中的通用组件、二次封装组件、主题变量和交互约定。
- 不要绕过项目既有规范，直接在页面内“各写各的”。
- 不要因为局部需求破坏整个系统的一致性。

---

## 组件使用总原则
- 能复用项目已有封装时，不要直接重复使用原生 Element Plus 基础组件造轮子。
- 表格、表单、弹窗、抽屉、上传、分页、筛选、搜索等高频能力，优先统一风格与交互。
- 公共场景优先抽象，不要在多个页面复制粘贴相同配置。
- 不允许因一个页面的特殊需求，擅自引入第二套大型 UI 组件库。
- 所有组件使用方式，优先遵循项目内约定的 props、events、slots、expose 能力，不要随意自创一套交互模式。

---

## 版本与基础约定
- 项目默认基于：
    - `vue@3`
    - `element-plus@2`
    - `vue-router@4`
    - `pinia`
- 所有 Element Plus 组件注册方式必须遵循项目统一方案：
    - 全局注册
    - 按需引入
    - 自动导入
- 不允许在不同页面中混用多套引入方式，导致维护成本上升。
- 组件 API 使用以当前项目锁定版本为准，不要直接照搬其它版本文档示例。
- 图标统一使用项目约定方案，例如：
    - `@element-plus/icons-vue`
    - 项目封装图标组件
- 不要一部分页面用 Element Plus 图标，一部分页面又混用其它图标体系且无统一规范。

---

## 主题与样式规范
- 涉及主题色、字号、圆角、阴影、边框、间距时，优先走：
    - `theme.ts / theme.js`
    - 全局样式变量
    - CSS Variables
    - SCSS 变量
    - 项目已有主题配置
- 不要在页面里硬编码大量颜色值、阴影值、圆角值。
- 不允许大量通过覆盖 `.el-*` class 的方式做全局污染。
- 非必要不要直接修改 Element Plus 内部 class 选择器样式。
- 如必须覆盖样式，优先局部作用域控制，避免影响全局其它页面。
- 样式覆盖优先级建议：
    1. 主题变量
    2. 组件封装层 class
    3. 页面局部 class
    4. 谨慎覆盖 `.el-*`

### 样式书写要求
- 优先使用语义化 class 名，不要使用纯表现型命名。
- `scoped` 仅用于页面局部样式隔离，不要误以为它能替代设计规范。
- 使用 `:deep()` 覆盖 Element Plus 内部结构时，必须控制作用域，禁止无边界覆盖。
- 不要在单个页面中堆积大量 patch 式样式修复，应优先回到封装层统一治理。

---

## 组件命名与封装规范
- 基于 Element Plus 封装的组件，命名必须体现业务语义或组件职责。
- 公共组件推荐命名：
    - `CommonTable`
    - `CommonForm`
    - `CommonDialog`
    - `CommonDrawer`
    - `CommonUpload`
    - `CommonSearchBar`
    - `CommonPageHeader`
- 页面私有组件放当前页面 `components/` 目录，不要直接上移到全局。
- 一个组件只承担一个主要职责，避免“巨型通用组件”。
- 通用组件禁止耦合具体业务字段名、接口名、路由名。
- 封装组件时，优先保持和 Element Plus 原生能力兼容，避免把常用能力封死。

### Vue 组件文件约定
- 组件文件名使用 PascalCase，例如：
    - `CommonTable.vue`
    - `DialogUserEdit.vue`
    - `FormOrderSearch.vue`
- 业务页面中的弹窗、抽屉、筛选区、详情区，优先拆分为独立组件，不要全部堆在页面主文件中。
- `script setup` 为默认推荐写法，除非项目已有统一例外约定。

---

## Layout 使用规范
- 布局优先复用项目已有 `layouts/` 目录方案。
- 固定侧边栏、固定顶部、响应式布局等由布局层处理，不要每个页面重复处理。
- 页面中不要重新定义系统级布局行为。
- 侧边菜单、Header、Breadcrumb、内容区容器风格必须尽量统一。
- 页面只关心当前业务内容，不负责系统级壳层结构。

### 推荐约定
- 系统级布局放在：
    - `layouts/BasicLayout.vue`
    - `layouts/BlankLayout.vue`
- 页面容器统一通过：
    - `PageContainer`
    - `CommonPage`
    - 或项目既有页面骨架组件
- 不要在业务页面内直接拼装完整的布局壳层。

---

## Menu 使用规范
- 菜单数据优先来源于路由配置或统一配置，不要在页面中硬编码。
- 菜单 icon 统一使用项目已注册图标或 Element Plus 图标体系。
- 菜单选中、高亮、展开逻辑优先依赖路由状态。
- 隐藏页、详情页如需高亮父菜单，应通过统一 `activeMenu` 机制处理。
- 不要在多个地方分别维护菜单结构。

### 菜单约定
- 菜单渲染优先由路由表中的 `meta` 驱动，例如：
    - `meta.title`
    - `meta.icon`
    - `meta.hidden`
    - `meta.activeMenu`
    - `meta.permission`
- 不要在组件内手工维护一套“伪菜单映射”。
- 不要把权限过滤、菜单过滤、选中逻辑混写在模板中，应抽离为计算逻辑或工具函数。

---

## Button 使用规范
- 按钮类型应明确表达操作语义：
    - 主操作：`type="primary"`
    - 次操作：默认按钮
    - 成功态操作：`type="success"` 仅在项目明确约定时使用
    - 警告态操作：`type="warning"` 仅在项目明确约定时使用
    - 危险操作：`type="danger"`
- 页面主按钮数量要受控，避免多个主按钮同时竞争视觉焦点。
- 危险操作必须具备明确确认机制。
- loading 状态要与异步操作绑定，避免重复点击。
- 不要为了“好看”滥用彩色按钮、plain、渐变等样式。

### 按钮交互要求
- 异步提交按钮必须绑定独立 loading 状态。
- 同一操作在表格行内、弹窗底部、页面头部的命名和语义要统一。
- 禁用按钮必须有明确原因，必要时给出提示。
- 不要把“返回”“取消”“关闭”全部做成同样的强视觉主按钮。

---

## Form 使用规范
- 表单优先统一使用项目内已有封装与书写方式。
- 新增、编辑尽量复用同一套表单结构。
- 表单项命名要与字段语义一致，不使用模糊字段名。
- 校验规则统一管理，避免散落在多个位置。
- 表单提交前后状态要完整：
    - 提交中 loading
    - 成功提示
    - 失败提示
    - 禁止重复提交

### Form 组织约定
- 推荐使用：
    - `el-form`
    - `el-form-item`
    - 项目统一的 form schema 封装
- 表单数据统一放在响应式对象中管理，不要把字段状态散落在多个 `ref` 中，除非字段天然独立。
- 表单默认值、回显值、提交参数转换应明确分层，不要混在模板中临时处理。

### Form.Item 约定
- `prop` 必须与字段含义一致。
- `label` 必须使用用户可理解的业务名称。
- 不要在 `el-form-item` 中塞过多复杂逻辑。
- 条件显隐复杂时，优先抽离组件或预处理配置。
- 不要在模板中直接写大段三元表达式控制表单逻辑。

### 表单交互要求
- 必填项明确标识。
- 禁用态、只读态、编辑态要有一致行为。
- 重置按钮应明确恢复到初始条件，而不是不确定状态。
- 弹窗表单关闭时，优先根据业务决定是否重置。
- 编辑回显时必须保证数据类型正确，例如：
    - `el-select` 的值类型
    - `el-date-picker` 的绑定值类型
    - `el-switch / el-checkbox` 的值语义

### 校验规范
- 校验规则优先统一抽离到：
    - `rules.ts`
    - `formRules.ts`
    - 或组件内独立常量区
- 同类字段校验规则保持一致，不要多个页面各写一套。
- 后端错误信息与前端校验提示要区分清楚，不要混为一类。
- 自定义校验函数要可复用，不要在多个组件里复制相同逻辑。

---

## Table 使用规范
- 表格列配置优先放在 `columns.ts`、`config.ts` 等独立文件中。
- 复杂列渲染不要直接堆在页面主文件中，应抽离成局部组件或独立 render 方法。
- 表格查询、分页、排序、筛选交互要统一。
- 表格必须考虑以下状态：
    - loading
    - 空数据
    - 错误态（如项目已有约定）
- 操作列按钮数量要克制，避免一行堆过多操作。

### columns 规范
- `label` 明确易懂
- `prop` 与数据字段一致
- `key` 稳定
- 自定义渲染保持简洁，不写大段业务逻辑
- 状态字段、时间字段、金额字段要按项目统一格式展示

### 表格交互建议
- 搜索条件与表格数据联动应可预期
- 分页参数要和查询条件一并维护
- 切换筛选时是否回第一页，要遵循系统统一习惯
- 行选择、批量操作必须具备明确提示和边界处理

### Element Plus Table 特别要求
- `row-key` 必须稳定，禁止直接使用不可靠索引。
- `el-table` 的 `formatter`、插槽、自定义单元格职责要清晰，不要混用失控。
- 表格滚动、固定列、固定头部、合计行等能力，优先走项目统一方案。
- 大表格场景需关注性能，不要在每个单元格渲染中创建大量新对象或新函数。
- 涉及树形表格、懒加载、展开行、选择联动时，必须先遵循项目统一交互约定。

---

## Dialog / Drawer 使用规范
- 页面中有多个弹窗时，必须拆分独立组件，不要全部堆在页面主文件。
- 弹窗名称要明确，例如：
    - `UserEditDialog`
    - `RolePermissionDrawer`
- 显隐状态命名必须清晰：
    - `userEditDialogVisible`
    - `rolePermissionDrawerVisible`

### 弹窗交互要求
- 打开时，初始数据要明确
- 关闭时，状态清理逻辑要明确
- 提交按钮要有 loading
- 二次打开时，不应残留脏状态
- 危险提交必须结合确认逻辑

### 选择 Dialog 还是 Drawer
- 简单编辑、确认、提示：优先 `Dialog`
- 较长表单、详情浏览、较复杂操作：可使用 `Drawer`
- 不要因个人偏好混用，保持系统统一

### Vue 中的状态控制建议
- 优先通过 `v-model` 或统一封装协议控制显隐。
- 子组件不要私自维护一份和父组件冲突的 visible 状态。
- 弹窗内部如需暴露打开方法，应通过 `defineExpose` 且有统一规范，不要多套风格并存。

---

## Message / Notification / MessageBox 使用规范
- 成功反馈统一优先使用 `ElMessage.success`
- 警告反馈统一优先使用 `ElMessage.warning`
- 错误反馈统一优先使用 `ElMessage.error`
- 重要系统通知可使用 `ElNotification`
- 删除、停用、批量操作等高风险动作，优先使用 `ElMessageBox.confirm`

### 反馈文案要求
- 简洁明确
- 说明动作结果
- 不要使用模糊文案，如：
    - “操作完成”
    - “处理成功”
- 推荐：
    - “删除成功”
    - “保存成功”
    - “状态更新成功”
    - “提交失败，请稍后重试”

### 反馈约定
- 同类动作的成功与失败提示文案应统一。
- 接口异常不要直接把原始错误堆给用户。
- 长耗时操作必要时结合按钮 loading、局部骨架屏、全局提示一起使用。

---

## Upload 使用规范
- 上传能力优先走项目已有封装。
- 上传前校验、文件大小限制、文件类型限制必须明确。
- 上传成功与失败都应有反馈。
- 上传返回结果结构必须统一处理，不直接把后端原始结构暴露给页面。
- 涉及 OSS、预览、回显、多文件管理时，优先复用现有工具函数与封装。

### Upload 约定
- 文件列表结构统一，不要有的页面存原始响应，有的页面存转换结果。
- 上传组件的受控与非受控模式要统一约定，避免状态混乱。
- 预览、删除、回显、排序、重新上传等行为要有一致交互。
- 手动上传与自动上传策略要在组件职责层面定义清楚。
- `before-upload`、`on-success`、`on-error`、`on-remove` 等回调职责明确，不要在各页面随意拼接流程。

---

## DatePicker / TimePicker 使用规范
- 日期时间处理统一使用项目既有方案，例如 `dayjs`。
- 展示格式、提交格式、查询格式要统一。
- 范围选择、起止时间边界、默认值逻辑要明确。
- 不要在不同页面对同类时间字段采用不同格式。
- 所有时间类组件必须明确：
    - 展示给用户的格式
    - 传给接口的格式
    - 组件内部绑定值的类型

### 日期处理要求
- 不要在模板中直接散写大量日期转换逻辑。
- 时区、起止时间边界、禁用日期规则要统一抽离。
- 查询场景与编辑场景的默认值策略要明确区分。
- `value-format` 使用必须统一，不要部分页面传 Date，部分页面传字符串且没有约束。

---

## Select / Cascader / TreeSelect 使用规范
- 选项数据优先配置化管理。
- 选项值与显示文案必须语义清晰。
- 异步选项加载必须处理 loading 与空状态。
- 不要在组件中散写大量 options 常量，优先放 `config.ts`。
- 下拉组件在大数据量场景要考虑性能与交互体验。

### 使用要求
- `value` 类型必须稳定，不要同一个字段一会儿 string 一会儿 number。
- 枚举类选项建议统一维护：
    - `enum`
    - `options`
    - 字典映射表
- 不要把接口返回原始字段直接散落映射到多个页面，应抽到统一转换层。
- 远程搜索、懒加载、可清空、多选等行为在同类字段中应保持一致交互。

---

## Tabs / Card / Descriptions 使用规范
- Tabs 用于同级信息切换，不要承载复杂隐藏式页面路由逻辑。
- Card 用于结构分组和信息承载，保持间距和层级统一。
- Descriptions 用于详情展示，不要混入大量可编辑行为。
- 多个视觉容器并存时，优先保证信息层级清晰，不要堆砌装饰。

### 交互要求
- Tabs 切换是否缓存、是否重置、是否联动查询条件要统一明确。
- Card 不要滥用嵌套，避免页面层级过深。
- 详情展示页面优先保持“可读”，不要为了视觉效果造成信息密度失控。

---

## icons 使用规范
- 图标统一使用项目统一图标方案。
- 如项目基于 `@element-plus/icons-vue`，则保持统一，不要混入多套风格。
- 图标必须表达业务含义，不要只为装饰而滥用。
- 菜单、按钮、状态标识中的图标风格尽量统一。
- 同一语义尽量复用同一图标，不要一个地方一个风格。

### 图标使用要求
- 菜单图标、按钮图标、状态图标分层使用，不要所有地方都加图标。
- 不要把图标当作唯一语义承载，必要时要有文字说明。
- 不要为追求“丰富”而让页面图标过载。

---

## 与路由和权限的协同规范
- 菜单、面包屑、页面标题优先由路由配置驱动。
- 页面按钮权限不要散写在视觉层，优先复用统一权限判断工具。
- 详情页、编辑页、隐藏页如需菜单高亮，应依赖统一配置，不在组件中手工处理。

### 路由协同约定
- 页面标题、菜单高亮、面包屑、缓存标记、权限标记优先通过 `route.meta` 统一管理。
- 不要在多个页面各自维护面包屑文案。
- 与布局相关的页面行为，例如是否隐藏侧边栏、是否全屏展示，应由路由配置控制。

### 权限协同约定
- 权限判断优先在：
    - 路由守卫
    - 权限指令
    - 权限工具函数
    - 按钮权限封装组件
      中统一处理。
- 不要在模板中到处散写复杂的权限判断表达式。
- 禁止仅在前端隐藏按钮而忽略后端权限校验。

---

## 与 Pinia / 状态管理协同规范
- 与页面级筛选条件、表格状态、用户配置相关的数据，优先评估是否进入 Pinia 管理。
- 不要把临时 UI 状态和长期共享状态混放在一起。
- 共享字典、全局枚举、用户信息、权限信息应有统一 store 管理。
- 不要在多个页面重复请求相同基础数据而不做复用。

### 状态边界建议
- 页面内部短期状态：优先组件内管理
- 多组件共享状态：优先 composables 或 Pinia
- 全局级别状态：进入 Pinia
- 不要为了“看起来统一”把所有状态都塞进 store

---

## 与 composables 的协同规范
- Element Plus 相关复用逻辑，优先沉淀为 composables，例如：
    - `useTable`
    - `usePagination`
    - `useDialog`
    - `useDrawer`
    - `useFormRules`
    - `useDictionaryOptions`
- composables 负责复用逻辑，不直接承担复杂视图渲染职责。
- 不要把大量组件实例引用、业务 API 调用、UI patch 全部揉进一个 composable。

---

## 模板书写规范
- 模板层只保留必要绑定和结构表达，不要堆积复杂业务逻辑。
- 复杂显示逻辑优先转移到：
    - `computed`
    - 格式化函数
    - composables
    - 配置项
- 不要在模板中链式调用多个方法处理展示文本。
- 插槽使用要清晰，不要为了“灵活”导致调用层过于晦涩。

### 推荐原则
- “模板做展示，脚本做逻辑，配置做复用”
- 表格列插槽、表单插槽、按钮插槽命名要统一，避免页面间风格差异太大。

---

## 性能与可维护性要求
- 不要在模板或渲染过程中创建大量重复对象、函数、配置。
- 表格 columns、表单配置、菜单配置优先抽离到配置文件。
- 重型页面优先拆分子组件，不要把全部 Element Plus 配置都堆在页面主文件。
- 公共配置要集中，避免同一交互规则散落在多个页面。
- 大型页面应关注以下问题：
    - 首屏渲染压力
    - 大量表单项响应式开销
    - 大表格自定义渲染性能
    - 弹窗多实例渲染成本
    - 频繁 watch 带来的副作用

### 性能建议
- 合理使用 `computed`
- 谨慎使用深层 `watch`
- 不要滥用 `watchEffect` 处理复杂业务
- 大对象响应式管理要有边界
- 不要把所有接口返回值都无脑塞进深层 reactive 对象

---

## 不建议的行为
- 不要直接复制 Element Plus 官网示例到业务页面后不做项目化改造。
- 不要大量内联样式覆盖组件外观。
- 不要一个页面写出多套按钮、表单、表格交互习惯。
- 不要跳过项目封装，直接各自为政。
- 不要仅为追求视觉效果破坏现有交互一致性。
- 不要在模板中直接写复杂匿名函数和大段判断逻辑。
- 不要把接口数据转换、权限判断、显示格式化全部揉进组件模板里。
- 不要在多个页面重复实现相同的搜索区、表格区、弹窗区。

---

## 修改 Element Plus 相关代码时的检查点
修改后优先检查：
- 页面布局是否正常
- 表单、表格、弹窗、抽屉是否还能正常交互
- 样式是否污染其它页面
- 主题变量是否仍然统一
- 调用方是否兼容
- 权限与菜单高亮是否正常
- 路由跳转和缓存逻辑是否正常
- 表单回显和提交数据格式是否正确
- 表格分页、筛选、排序是否联动正常
- 弹窗重复打开是否存在脏状态
- 上传、预览、删除流程是否完整
- 日期时间字段是否仍符合统一格式要求
